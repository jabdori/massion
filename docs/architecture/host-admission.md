Bounded first to one distinct Mission/Work admission at a time using in-memory owned-runtime tracking (PR47), then stage 1 (2026-11-17) replaced the refusal with a durable run queue the host continues by itself: a run request that meets a busy, draining or backlogged host joins the host-wide `run-queue` aggregate instead of being refused, and one taker starts the entries in sequence order when the slot is handed over. ## Stage 1: the durable run queue

The approved screen B18 shows two members' Work "running" at once. Stage 1 does not deliver that: one Work runs, the other waits in the queue, and its card shows today's "not started" text (the conversation card classifies an unstarted Work as 시작 전 with a Start button; a queued Work keeps exactly that appearance, and pressing Start joins the already-queued request again, changing nothing). Several slots are stage 2; slices Q1b (the schedule's run record), Q2 (parking a browser approval) and Q3 (parking a credential repair) are later changes on top of this aggregate.

An entry records the Mission id, the Work binding (`SequenceWork`: workId, inputHash, criteriaHash), the time it joined, a monotonic sequence number, who requested (owner or assistant), the run id `activate-runtime` will need, and the execution choice made at request time. Order is the sequence number. A request whose `expectedRevision` no longer matches is refused with the same conflict an idle host returns; joining never widens it. At its turn the entry carries no permission: the single taker re-runs today's admission against the state at that moment, comparing the entry's hashes with the Work (not the Mission revision, so a sibling Work committing in the same Mission does not fail a waiting entry), and re-checking the fence, the stored settings and the member routing through the normal run path; the admission then expects the revision of the snapshot the taker compared, so a change between that comparison and the activation commit is a conflict exactly like a direct request. A direct request only returns a refusal and records nothing; the taker, having nobody to return a refusal to, records a final one (the member is gone or archived, the input changed, the connection or authorization is gone, the Work is cancelled, already started or budget-waiting) on the Work through the existing `block-work` command before removing the entry — the command id carries the entry's sequence number so a repeated refusal records again, and a budget-waiting, cancelled or already-started Work keeps its own state as the reason — while a transient refusal (`settings_pending`, a fence or store that could not be read, any unknown code, or a final code mixed with one of those) keeps the entry stored for the next trigger. A removal that fails, or a reason that cannot be recorded, halts the queue: while halted no entry is taken and no pass starts anything (the head would otherwise run twice), joins still work, the halt (a closed code and the entry's ids) is part of the host status response, the server marks the host unsettled through the same flag its start-up resume and monthly reconcile already set, and a host restart clears the halt — the durable queue still holds the entry, and `work_already_started` keeps a Work that already ran from running again. What today's preflight leaves out and `run` checks later stays that way at the turn: the monthly budget is first tested inside the run (budget-waiting drops the entry). The run path reads the members aggregate at admission, so a Work of a member who is gone or archived is refused for a direct request and for a queued entry alike, an explicit choice included (`member_unknown`, `member_archived`).
