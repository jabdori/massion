## Stage 1: the durable run queue

The approved screen B18 shows two members' Work "running" at once. Stage 1 does not deliver that: one Work runs, the other waits in the queue, and its card shows today's "not started" text (the conversation card classifies an unstarted Work as 시작 전 with a Start button; a queued Work keeps exactly that appearance, and pressing Start joins the already-queued request again, changing nothing). Several slots are stage 2; slices Q1b (the schedule's run record), Q2 (parking a browser approval) and Q3 (parking a credential repair) are later changes on top of this aggregate.

An entry records the Mission id, the Work binding (`SequenceWork`: workId, inputHash, criteriaHash), the time it joined, a monotonic sequence number, who requested (owner or assistant), the run id `activate-runtime` will need, and the execution choice made at request time. Order is the sequence number. At its turn the entry carries no permission: the single taker re-runs today's admission against the state at that moment, comparing the entry's hashes with the Work (not the Mission revision, so a sibling Work committing in the same Mission does not fail a waiting entry), and re-checking the fence, the stored settings and the member routing through the normal run path. A failed check removes the entry and leaves the Work with the same blocked shape a direct request would have produced; a budget-waiting Work loses its entry because the budget path requests again; a cancelled Work's entry is removed without a run. What today's preflight leaves out and `run` checks later stays that way at the turn: the monthly budget is first tested inside the run (budget-waiting drops the entry), and for entries with an explicit choice there is no cheap member-liveness check in today's run path beyond the fence, so none was invented.
