# Exact stored memory identities in usage reads

Approved correction above Draft #69 `53f7c0a0b1178b7f4602797c2fbb23ce3ac098ea`, tied to MEM-01, ADR0001 and open issue #4 historical input inspection. Existing memory saving and portable lineage allow literal nonblank, well-formed IDs up to 16,000 UTF-16 units. `readMemoryUsage` instead restricts them to an ASCII 128-character identifier. The normal selector already keeps an exact JSON ID/version tuple and URL-encodes the original ID; the reader rejects valid stored identities, including Unicode, CR/LF, spaces and punctuation.

Change only that reader ID validation to the existing lineage contract. Do not trim, normalize Unicode/newlines, substitute latest versions, change saving/UI/Work/Record identity rules, expand other query fields or grant authority. Version/hash/feed validation, single authoritative snapshot, original hash and lineage checks, historical/inactive reads, 20-use bound, and stale/late/feed guards remain.

Acceptance: reproduce normal actual-DB/CLI/headless keyboard reads rejecting a stored literal ID before the fix; after the fix, read original ID/version/hash/content/source and exact retained accepted Record/fresh Work pins across v1/v2/retirement and restart/portable restore. Distinct LF versus CR/LF and composed/decomposed IDs must never alias. Invalid empty/blank/ill-formed/over-bound IDs still reject before store access. Wrong version/hash/feed, malformed/duplicate/extra HTTP queries, tampered lineage, late replies after Cancel/selection/Mission/revision/feed changes remain rejected or discarded. Snapshot/journal/old Work/Record are unchanged, with zero write/provider/model calls for reads. Actual DB, normal CLI/headless keyboard, affected regressions, independent read-only review, small Draft and exact-head CI. No other feature/input-rule changes, merge/deploy, real models, permissions/spending or new resources.
