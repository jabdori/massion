# Mission discussion before first Work

Above DraftPR66 `5a3481dab0fafeb39c13039bbfcde13872f7d14a`, COL-01/SUR-01 and the Mission→Work purpose in ADR0001/issue #4 need durable owner discussion before a concrete Work exists. Existing conversation threads require an existing Work, forcing admission before owner deliberation. This increment supports one Mission-level owner thread and reuses the separately reviewed saved-message→new-Work path. It is not another automatic planning system.

Existing Conversation retains its exact fields, with `workId:null` explicitly representing the Mission thread. Its deterministic ID hashes that same null scope and Mission ID; strings keep their original Work-bound IDs and bytes. One null thread per Mission, owner author, original message ID/ordinal/text and earlier same-thread reply rules, global message uniqueness, existing100-thread/100-message/4KiB-text/256KiB-thread/1MiB-Mission limits remain. `append-mission-message` accepts exactly messageId/replyTo/text/type; normal `POST /missions/:id/mission-message` accepts commandId/expectedRevision/messageId/replyTo/text and never caller Work/role/author/ordinal/grant. CAS/feed/frozen caller/replay/exact receipt and immutable no-edit/delete history apply. Read-only `GET /missions/:id/mission-conversation` uses one fresh snapshot/feed/cursor with no query keys or fallback. Work0 and terminal/unknown Work do not prohibit ordinary Mission discussion or alter their evidence.

Existing conversationSource selection can explicitly name `workId:null` plus exact messageID/hash. Capture pins the original Mission-thread ID/message/owner decision; old string Work sources/Records remain byte-identical. New Work title is a separately edited task, never implicit instruction/permission from discussion. Its original source enters the existing input hash, both text roles and accepted Record through the unchanged execution/Assurance/Records path. Original messages/replies and other Work/Record stay unchanged; subsequent discussion never replaces a pin. Browser task draft line-break normalization must be visibly distinguished from immutable original source before explicit review/admission.

Reuse normal conversation controls with an explicit Mission/Work scope selector; preserve separate private drafts/reply/base/feed by Mission+scope/Work. No initial write, automatic reply/task admission/run or model context. Pending/unknown locks, stale/ABA/current-source review, late replies, changed Mission/feed and restart preserve exact identities and no replay. Reuse saved-message Work review/cancel/save; Run remains separately explicit. New actor responses, assistant/Representative communication, semantic task extraction, global conversations/shared model context, authenticated identities and automatic collaboration are separate open contracts, not chosen here. No new execution authority or indispensable user policy decision in the bounded owner-only scope.

Acceptance: actual DB/API Mission with0Work→literal owner message→same-thread reply→read from two independent clients and restarted host→explicit edited source-selected Work→separate controlled Run/Record; original source/input/checksum and old Work/thread/Record preserved. Reject foreign thread/Mission replies, duplicate IDs/forged scope/roles/fields, malformed/bounds, stale/wrongfeed/tampered source and caller mutation; native CAS/replay/journal/restart/portable restore including legacy string sources. Client exact-source review/cancel/unknown/lost/late/otherMission/feed/ABA/moved focus and no automatic reload POSTs. Normal CLI/fresh Chrome keyboard Work0 discussion/reply→source review/Cancel/Work admission→restart, narrow/wide layout and literal Unicode/LF/CR behavior. Appropriate affected regression, independent exacthead read-only review, small Draft and push/PR actual DB CI. Live model/semantic quality, production auth, scheduling/recovery and broader conversation completion remain open.
