# Explicit bounded Work sequence

Before implementation: PR48 a933b12 preserves one distinct normal local Work slot and explicit busy rejection. The charter's product-owned causal Work → independent Assurance → Records completion (WRK-01/COL-01/ASR-01/GOV-01/RUN-01, issue4) still requires one owner Run for every ready successor, even with exact existing prerequisite pins. Add a normal headless owner-requested sequence of at most3 exact already-admitted fresh Work, not a durable queue or new domain state/command. The reviewed Mission revision, ordered Work IDs/input/criteria hashes and existing execution selection authorize only those exact requests in this process. No implicit Work creation, profile/grant, prerequisite rebinding, replay, late receipt settlement or new ownership scheme.

Acceptance: freeze caller input before awaits; strict bounds/unique IDs/exact hashes. Validate fresh original Work and prerequisite order/pins before any run, allowing only explicitly earlier selected fresh prerequisites whose future accepted Records must be checked by the existing runtime. Existing external prerequisites must already resolve. First revision and original configuration are inspected; each later step starts only from the last accepted snapshot revision and same original configuration, never silently rebases across other owner writes. Stop on first nonaccepted result, unknown/error, changed input/configuration/revision, busy, cancellation or drain. The complete original unstarted Work (including budget) must still match its initial inspected state before its admission, including owner changes while a prior run was in flight. Existing run internals retain their own concurrent-read/CAS behavior; unrelated conversation writes observed inside an accepted run are not a universal global write lock. Each stage uses normal preflight/run with stable derived individual run command IDs; original provider claim/receipt/deadline/cancellation behavior is unchanged. There is no whole-sequence atomic transaction; confirmed earlier accepted Work remains accepted after later stop.

A repeated request starts at its first requested Work and stops if that Work is already admitted, without skipping it or starting later fresh Work. Stable command IDs are based only on submitted sequence identity and index (not changed payload), so same identity cannot silently authorize a different Work at that position. Interrupted/unknown/accepted originals are never replayed. Restart grants0 and no restored plan/automatic dispatch. Unstarted remaining Work requires a new explicitly reviewed request and current existing authorization.

## Normal headless protocol

POST `/missions/:id/run-sequence` with `commandId`, `expectedRevision`, `works: [{workId,inputHash,criteriaHash}, ...]` and the existing `selection: {executorProfileId,verifierProfileId,authorizationId,outputTokenCap}`. Select exactly1..3 distinct already-admitted Work in reviewed order, with prerequisites already declared through `/work-prerequisite`. Use `workInputHash(work)` and `hash(work.criteria)` exported by `src/domain.ts` against one inspected Mission snapshot. In the local source checkout a headless client can import those pure helpers under Node24, retain that snapshot revision and submit the exact bindings; it must not refetch/rebase automatically. Existing `X-Massion-Feed` binds admission to the inspected database. Configuration/authorization must already exist; this endpoint grants nothing.

A200 result is `completed` only if every requested Work has an independently accepted Record. `stopped` names confirmed completed Work IDs and the first nonaccepted stage, with its normal `blocked/cancelled/already-started/conflict/settled` classification and original snapshot. Later stages are not run. `settled` without accepted Assurance stops the sequence. CAS conflict returns409. Exact preadmission input/order violations return400, and the existing503 unknown/admitted-unsettled response retains the original individual run identity/snapshot. No error or lost outer response authorizes retry or skipping completed stages. Read existing Work/Record/run-ownership/operation receipts to inspect outcomes.

Individual run IDs are `sequenceRunId(commandId,index)` from `src/run-sequence.ts`. They bind only the original outer identity and0-based stage index, so changed payload/order cannot bypass an already committed stage identity. An outer sequence has no independent durable receipt and is not an atomic command: only the ordinary individual activation/claim/receipt/acceptance journals establish results. An aborted caller does not cancel the owned Work; host drain still owns normal runtime closure. A new explicit plan may include only genuinely unstarted remaining Work and requires newly inspected revision/configuration. Do not carry old host grants across restart.
