# ADR-002 — 지식 축과 표면 복원

[English](ADR-002-knowledge-axis-restoration.md) | [한국어](ADR-002-knowledge-axis-restoration.ko.md)

> **상태:** 승인됨
> **승인일:** 2026-07-27
> **대상:** 제품 헌법 §5 제품 모델, §6 Surface

## 맥락

헌법 §4.3은 조직 이름이 바뀌어도 보존해야 할 운영 책임 일곱을 불변량으로 선언합니다.

```
Control · Strategy · Evidence · Delivery · Assurance · Records · Growth
```

그런데 §5 제품 모델의 축은 여섯이고 **Evidence가 빠져 있습니다.** §6 표면은 §5 축의 투영이므로 표면에서도 함께 빠졌습니다.

| 축 | 표면 |
|---|---|
| 조직 | 조직 |
| 업무 | 업무 |
| 실행·협업 | 업무 안 협업방 |
| 결정 | 수신함 |
| 성장 | 개선 |
| 역량 | 확장 |
| **Evidence** | **축·표면 모두 없음** |

도메인은 그 책임을 그대로 구현했습니다. `packages/evidence`가 Tree-sitter 기반 SourceFile·Symbol·Chunk·Relation 인덱스, exact·BM25 검색, `CodeGraphService`, `EvidenceBrief`를 갖고 있고, Core Office의 `evidence-research`(Quill)가 이 책임의 조직 노드이며, 생산 server가 `WorkspaceKnowledgeService`로 Work intake에 조립합니다.

**갈 곳 없는 구현이 `work.knowledge` 한 조각으로만 새어나왔습니다.** 계약은 Work 하나가 인용한 코드 범위만 노출하고, 관계·인덱스·검색·저장소는 하나도 노출하지 않습니다. §5의 "업무" 축에 `Context`가 있지만 그것은 `ContextVersion`(목적·범위·제약·가정)이라 코드 지식의 대체재가 아닙니다.

즉 이것은 새 제품 정체성 추가가 아니라 **§4.3이 이미 선언한 불변량을 §5·§6에 맞추는 정합**입니다.

## 결정

### 1. §5에 지식 축을 복원합니다

| 축 | 답하는 질문 | 핵심 객체와 결과 |
|---|---|---|
| 지식 | 조직이 무엇을 알고 있는가? | Workspace, Repository, IndexVersion, Symbol, Chunk, Relation, EvidenceBrief |

### 2. §6에 `지식` 표면을 추가합니다

표면 집합은 여섯에서 일곱이 됩니다: `홈 · 업무 · 조직 · 개선 · 확장 · 지식 · 설정`. 전역 레일 순서는 업무 다음, 조직 앞입니다. 업무가 쓰는 재료이고 조직보다 자주 열기 때문입니다.

`지식` 표면이 답하는 질문은 **"조직이 내 워크스페이스에 대해 무엇을 아는가"**입니다. 업무의 `근거` 탭과 겹치지 않습니다.

- `지식` 표면 = 서가. 워크스페이스 범위, 현재형.
- 업무 `근거` 탭 = 이 Work가 실제로 인용한 것. Work 범위, 과거형.

인용 목록으로 서가를 대신할 수 없고 반대도 마찬가지이므로 둘 다 유지합니다.

### 3. 마인드맵을 탐색 모델로 채택합니다

렌즈는 **업무·문서·파일 셋**입니다. 심볼은 렌즈로 두지 않습니다 — 1,800개를 한 캔버스에 펼치면 찾을 방법 없이 점만 많고, 알고 싶은 "이 심볼이 무엇과 엮였나"는 파일을 눌렀을 때 시트와 업무 `근거` 탭이 이미 답합니다. 자료는 그대로 남고 지도만 뺍니다.

**캔버스는 같은 종류끼리만 잇습니다.** 업무 지도에는 업무만, 파일 지도에는 파일만 있습니다. 종류를 섞으면 "무엇의 지도인지"가 사라집니다. 이종 연결은 노드를 눌렀을 때 시트가 보여줍니다 — 이 파일이 어떤 업무들에 쓰였고 어떤 문서들이 설명하는지가 거기서 답해집니다.

같은 종류를 잇는 근거는 직접 관계(파일 `imports`, 심볼 `calls`·`implements`)이거나 공유한 것(업무끼리는 같은 파일·문서를 건드려서 이어짐)입니다. 후자는 무엇을 공유했는지 이름을 함께 실어 보내고 화면이 점선으로 구분합니다.

**색은 폴더에서 나옵니다.** 무작위로 칠하면 색덩이가 아무 뜻도 없어 눈만 피로해집니다. 폴더로 칠하면 뭉친 색이 곧 "이 영역이 서로 많이 부른다"는 사실이 됩니다. 에이전트 팔레트보다 채도를 낮춰 두 색 언어가 겨루지 않게 합니다.

**렌더링에 ReactFlow를 쓰지 않습니다.** ReactFlow는 노드 에디터라 지식 그래프의 생김새가 나오지 않습니다. 점·선·라벨을 SVG로 직접 그리고 배치는 결정론적 force 계산으로 얻습니다. 조직 지도는 고정 계층 트리라 성격이 달라 ReactFlow를 유지합니다.

### 4. 상세는 오버레이가 아니라 열리는 시트를 씁니다

노드를 누르면 오른쪽에 시트가 열려 그 노드의 내용과 **모든 종류의 연결**을 보여줍니다. 목록 항목을 누르면 그리로 옮겨가고, 업무 노드는 그 업무 화면으로 갑니다.

시트는 화면을 덮는 오버레이가 아닙니다 — 이 앱에서 오버레이는 이미 `수신함`의 뜻이고, 시트는 표면 안의 열입니다. 아무것도 고르지 않으면 시트가 없고 캔버스가 폭을 다 씁니다. 그래서 열은 고정 3열이 아니라 고를 때만 셋이 됩니다.

### 5. 관계 통합은 application 계층에서 합니다

관계 저장소가 셋으로 갈려 있습니다.

| 저장소 | 관계 |
|---|---|
| evidence | `contains · imports · calls · implements · documents` |
| organization | `OrganizationReference.kind` — work·agent·task·conversation·memory·approval·permission·prompt·skill·extension |
| growth | `source_reference_ids` — work:·message:·verification:·organization:·execution:·artifact: |

단일 간선 테이블이 없으므로 **application 계층 조인으로 하나의 이웃 조회를 만듭니다.** SurrealDB native relation(`RELATE`) 전환은 §9.6이 "순회 성능 실패가 측정될 때만" 열라고 정했으므로 이 ADR은 그 문을 열지 않습니다. LSP와 embedding provider도 같습니다.

## 결과

- 헌법 §5 축 표와 §6 표면 목록을 개정합니다.
- 데스크톱에 `지식` 표면을 추가합니다. 열1(워크스페이스)은 `workspace.*` 계약으로 실제 동작하고, 열2·열3은 계약이 열릴 때까지 완성본 fixture로 둡니다.
- 조회 셋은 `knowledge.index`(색인 규모·제외), `knowledge.graph`(렌즈별 동종 지도), `knowledge.links`(고른 노드의 전종 연결)로 나눕니다.
- 업무 `근거` 탭은 같은 관계 데이터를 Work 범위에서 쓰는 소비자로 유지합니다.

## 대안과 기각 이유

- **업무 안 탭으로만 유지** — Work 범위를 벗어난 질문(워크스페이스 인덱스 상태, Work 밖 탐색)을 답할 수 없습니다. 누락의 원인을 그대로 둡니다.
- **전체 그래프 뷰어** — 노드 수에 따라 읽을 수 없게 됩니다. 조직 지도에서 실측으로 실패했습니다(잉크 점유율 0.65%).
- **한 캔버스에 모든 종류 섞기** — "무엇의 지도인지"가 사라지고, 이종 연결은 시트가 더 정확히 답합니다.
- **SurrealDB native relation 선행 도입** — §9.6이 정한 측정 조건 없이 여는 것이라 기각합니다.
