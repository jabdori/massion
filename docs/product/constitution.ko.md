# Massion 제품 헌법

[English](constitution.md) | [한국어](constitution.ko.md)

> **역할:** 제품 정체성의 최상위 정본
> **대상:** 제품·아키텍처·화면·AgentOS를 설계하고 검토하는 사람
> **변경 규칙:** 제품 정체성이나 불변량을 바꾸려면 사용자 승인과 아키텍처 결정 기록(ADR)이 필요합니다.

## 1. 이 문서가 소유하는 것

이 문서는 Massion이 왜 존재하고 무엇을 지켜야 하는지 정의합니다. 프레임워크, 데이터베이스, UI와 패키지 구조가 바뀌어도 제품 정체성을 편의에 맞게 다시 해석하지 않습니다.

문서와 코드의 책임은 다음과 같습니다.

1. 이 문서는 제품의 목적, 철학, 불변량과 경계를 소유합니다.
2. [`docs/architecture/README.ko.md`](../architecture/README.ko.md)는 시스템 책임과 데이터·신뢰 경계를 설명합니다.
3. ADR과 날짜별 설계는 특정 결정의 맥락과 선택을 보존합니다.
4. 코드는 특정 커밋의 동작을 정의합니다.
5. 후보 SHA에 결속된 검증은 제품·아키텍처 문서와 분리합니다.

코드가 이 문서의 방향을 충족하지 못하면 그 차이는 제품 갭입니다. 코드에 맞추려고 제품 목적을 축소하지 않고, 제품 문장을 근거로 존재하지 않는 동작을 주장하지도 않습니다.

## 2. 한 문장 정의

Massion은 사용자가 하나의 사명(Mission)을 맡기면 에이전트들이 실제 조직처럼 책임을 나누어 영속 업무(Work)를 수행하고, 사용자가 선택한 권한 경계와 검증·기록을 거친 경험으로 조직·기억·정책을 발전시키는 로컬 AgentOS입니다.

> 사람이 지시하고, 조직이 책임지며, 근거가 판단하고, 기록이 기억하며, 검증된 경험만 다음 조직을 바꿉니다.

## 3. 제품의 주권자

사람 사용자가 AgentOS의 최종 주권자입니다. 대표 에이전트(Representative)는 요청을 접수하고 조직을 조정하는 기본 창구이지만 사람의 권한을 대체하지 않습니다.

사용자는 다음을 결정할 수 있어야 합니다.

- 어떤 Work를 시작하고 중단할지
- 어떤 Workspace와 파일을 신뢰할지
- 어떤 Provider 계정을 연결할지
- 어떤 행동을 자동화하고 어떤 행동을 검토할지
- 어떤 조직·Prompt·Memory·Policy 변경을 채택하거나 되돌릴지

## 4. 변하지 않는 제품 원칙

### 4.1 한 명의 AI가 아니라 조직을 운영합니다

에이전트는 일회성 프롬프트가 아니라 책임과 권한을 가진 조직 구성원입니다. 조직은 요청에 따라 일을 나누고, 인계하고, 서로 검토하며, 결과를 하나의 Work에 귀속합니다.

기본 책임 언어는 다음과 같습니다.

- 대표 에이전트(Representative): 요청 접수, 전체 조정과 최종 응답
- 맥락과 전략(Context & Strategy): 목적, 위험, 계획과 완료 기준
- 근거 조사(Evidence & Research): 코드·문서·외부 근거와 인용
- 거버넌스(Governance): 정책, 권한과 사람의 결정
- 실행 조정(Delivery Coordination): Task 분해, 배정과 전문 실행
- 독립 검증(Assurance): 실행 주체와 분리된 품질 판정
- 기록(Records): 결정, 결과, 변경과 운영 기록
- 자가개선(Growth): 제안, 평가, 채택, 효과와 되돌리기

부서명과 팀 구조는 바뀔 수 있지만 이 책임들은 생략할 수 없습니다.

### 4.2 조직은 버전된 운영 구조입니다

조직은 정적인 조직도가 아닙니다. 업무 필요와 근거에 따라 생성, 활성화, 이동, 분리, 병합, 비활성화와 복구가 가능한 영속 구조입니다.

조직 변경은 다음 순서를 따릅니다.

1. 현재 요청과 보유 Capability를 확인합니다.
2. 기존 조직으로 처리할 수 있는지 판단합니다.
3. 부족한 책임과 필요한 팀·전문가를 제안합니다.
4. 영향, 권한과 되돌리기 조건을 검토합니다.
5. 허용된 변경만 새 Organization Version으로 적용합니다.

조직 생성 자체가 목적이 되어서는 안 됩니다.

### 4.3 대화가 아니라 Work와 사건이 정본입니다

대화는 요청·협업·개입을 위한 인터페이스입니다. 실행과 복구의 정본은 Work와 버전된 사건입니다.

Work에는 다음이 귀속됩니다.

- 사용자 요청과 목적
- Workspace, 맥락, 조직, 정책, Prompt와 Memory 버전
- 계획, 완료 기준과 Task
- 담당 Agent와 Assignment
- Collaboration Room과 구조화된 메시지
- 실행, Tool 사용, 산출물과 사용량
- 승인, 결정, 검증과 기록
- 실패, 차단, 취소와 복구 조건
- Growth 제안으로 이어지는 원인 계보

화면이나 모델이 바뀌어도 같은 Work를 이어서 운영할 수 있어야 합니다.

### 4.4 실행 엔진은 두뇌이고 Massion은 정책의 소유자입니다

VoltAgent와 Provider SDK는 추론, Tool 호출과 실행 재개를 담당하는 메커니즘입니다. Massion은 다음 정책을 직접 소유합니다.

- 누가 어떤 책임과 권한을 가지는가
- 어떤 요청이 어떤 Work와 조직에 귀속되는가
- 언제 계획·근거·승인·검증이 필요한가
- 무엇을 완료로 인정하는가
- 어떤 기억·조직·정책 변경을 채택하는가

특정 프레임워크나 Provider를 제품 정체성으로 승격하지 않습니다.

### 4.5 완료는 모델의 선언이 아닙니다

실행 주체의 성공 응답, 산출물의 존재와 테스트 한 번의 통과만으로 Work를 완료하지 않습니다. 완료에는 다음이 필요합니다.

- 명시적인 완료 기준
- 실행 책임과 분리된 Assurance
- 근거와 실패를 포함한 판정
- Records의 원자적 확정
- 재시작 뒤에도 같은 결론으로 수렴하는 계보

모델·Provider 후보 소진처럼 복구 가능한 조건은 실패로 위장하지 않고 `blocked`로 보존합니다.

### 4.6 자동화와 전체 권한도 사람의 선택에서 출발합니다

일반 실행은 정책, 필수 승인, Workspace 경계와 감사를 보존합니다. 자동 실행은 미리 허용된 범위에서 개입 빈도를 줄일 뿐 통제 장치를 없애지 않습니다.

전체 권한(full-access)은 사용자가 위험을 확인하고 직접 선택한 경우에만 현재 OS 사용자 권한으로 실행합니다. 이 선택도 schema, revision, checksum, 멱등성, 완료 검증과 Growth의 효과·되돌리기를 제거하지 않습니다.

정지는 실행이 보이는 Work 안에 있어야 합니다. 전역 위험 버튼을 중복해서 만들지 않고, 사용자가 현재 Work의 실행을 즉시 중단할 수 있게 합니다.

### 4.7 Provider가 제품 상태를 소유하지 않습니다

모델 계정과 네트워크가 없어도 조직, Work, 기록, 승인, 취소와 진단은 제한 모드에서 동작해야 합니다. Provider의 session, transcript와 quota는 Massion의 영속 상태를 대신하지 않습니다.

모델 선택은 capability, 데이터 정책, 비용, 평가와 계정 상태를 통과한 후보 안에서 이루어집니다. 사용자는 Provider와 예산 경계를 관리하지만 각 Work마다 내부 모델 경로를 수동 조립하지 않습니다.

### 4.8 자가개선은 근거 기반의 보수적 채택입니다

자가개선(Growth)은 모델이 자신을 즉시 수정하는 기능이 아닙니다. 다음 계보를 보존하는 변경 관리입니다.

- 원인 Work·Event·Evidence
- 변경 대상과 전후 버전
- 독립 신호와 반대 증거
- 평가 결과와 사람 또는 정책의 결정
- 후속 Work에서 측정한 효과
- 악화 시 되돌리기

새 버전은 이후 Work부터 적용하며 과거 계보를 다시 쓰지 않습니다.

### 4.9 지식과 기억의 권위를 분리합니다

지식(Knowledge)은 Workspace의 코드·문서·관계와 출처를 설명합니다. 기억(Memory)은 사용자가 명시했거나 검증된 경험에서 채택된 지속 문맥입니다.

- 지식은 Repository와 IndexVersion에 결속됩니다.
- 인용은 파일·문서·심볼과 source revision을 가리킵니다.
- 개인 기억은 다음 Work부터 적용되며 사용 중지할 수 있습니다.
- 모델의 일회성 transcript를 조직의 사실이나 영구 기억으로 승격하지 않습니다.

### 4.10 Extension은 조직의 역량을 늘리되 OS를 장악하지 않습니다

Extension은 Tool, Skill, 연동과 전문 실행 능력을 추가할 수 있습니다. 그러나 Core process, 데이터베이스와 credential을 직접 소유하지 않습니다.

Extension 실행에는 artifact 출처, manifest, 권한, 승인, 제한된 RPC, 감사와 수명 주기 계보가 필요합니다. 비활성화·업데이트·되돌리기는 기존 Work의 과거 사실을 변경하지 않습니다.

### 4.11 로컬 우선입니다

첫 제품 경계는 한 명의 사용자가 자기 Mac에서 운영하는 macOS arm64 데스크톱입니다. 데이터와 Provider 계정은 사용자의 로컬 경계 안에 있고, 앱 창과 daemon의 수명은 분리됩니다.

로컬 우선은 보안·복구·감사를 생략한다는 뜻이 아닙니다. 오히려 설치, 권한, backup·restore, 재시작과 비밀 저장의 책임을 제품이 명확히 소유해야 한다는 뜻입니다.

### 4.12 조직 운영은 관료주의가 아닙니다

단순한 요청에 불필요한 회의·승인·문서를 강요하지 않습니다. 위험, 불확실성, 영향과 전문성이 커질 때만 책임을 더 나눕니다.

좋은 조직 운영은 단계 수가 아니라 다음으로 평가합니다.

- 사용자가 현재 상태와 다음 행동을 이해할 수 있는가
- 책임과 결정 근거를 추적할 수 있는가
- 실패와 재시작 뒤에도 정확히 수렴하는가
- 실행 비용보다 검증 가능한 가치가 큰가

## 5. 제품 모델

### 조직(Organization)

책임, 관계, 권한과 Capability를 가진 버전된 운영 구조입니다.

### 업무(Work)

사용자 요청부터 실행·검증·기록·개선까지 이어지는 영속 실행 단위입니다.

### 협업방(Collaboration Room)

하나의 Work에 귀속된 사용자와 Agent의 구조화된 협업 공간입니다. 메시지는 답장, 원인, 작성자와 실행 계보를 가집니다.

### 결정(Decision)

실행 승인, 조직 변경, 권한 증가와 Growth 채택처럼 사람 또는 정책의 판단이 필요한 상태입니다.

### 산출물(Artifact)

Work가 만든 문서, 코드, 패치와 보고서입니다. 존재만으로 완료를 뜻하지 않습니다.

### 검증(Assurance)

완료 기준에 대한 독립 판정입니다. 실행 주체와 같은 근거를 반복하는 것이 아니라 별도의 기준과 실패 증거를 사용합니다.

### 기록(Records)

Work의 결정, 검증, 결과와 운영 변경을 보존하는 영속 기록입니다.

### 개선(Growth)

검증된 경험에서 새 버전을 제안하고 효과를 측정하며 필요하면 되돌리는 과정입니다.

## 6. 제품 표면

| 표면 | 답해야 하는 질문 |
|---|---|
| 홈 | 지금 무엇을 보거나 결정해야 하는가? |
| 업무 | 이 Work는 어디까지 왔고 무엇을 기다리는가? |
| 지식 | 조직이 이 Workspace에 관해 무엇을 알고 근거는 무엇인가? |
| 조직 | 누가 어떤 책임과 관계로 일하는가? |
| 개선 | 무엇을 배웠고 무엇을 바꿀 것인가? |
| 확장 | 조직에 어떤 Capability를 추가할 수 있는가? |
| 프로바이더 | 어떤 모델 공급과 계정이 사용 가능한가? |
| 예산 | 어떤 모델이 왜 선택됐고 무엇을 얼마나 썼는가? |
| 설정 | 사람이 어떤 지속 경계를 정했는가? |

전역 수신함은 별도 도메인이 아니라 어느 화면에서나 사람의 주의가 필요한 상태를 여는 진입점입니다. 표면은 서로의 책임을 복제하지 않고 같은 Work와 Application 상태를 공유합니다.

## 7. Massion이 아닌 것

- 모델을 골라 대화하는 범용 채팅 클라이언트가 아닙니다.
- 에이전트 프로세스를 여러 개 띄우는 런처가 아닙니다.
- 완료를 모델의 자신감이나 마지막 문장으로 판정하는 자동화 도구가 아닙니다.
- 사용자의 Provider 계정과 데이터를 중앙 서비스가 소유하는 프록시가 아닙니다.
- 근거와 효과 평가 없이 스스로 Prompt를 바꾸는 자기수정 시스템이 아닙니다.
- 설치 수만으로 조직의 Capability가 늘었다고 주장하는 Marketplace가 아닙니다.

## 8. 제품 판단 기준

새 기능, 화면 또는 아키텍처는 다음 질문을 통과해야 합니다.

1. 실제 조직 책임을 더 명확하게 하는가?
2. 사용자가 조직을 통제하고 실행을 중단할 수 있는가?
3. 결과가 영속 Work와 인과 계보에 귀속되는가?
4. 필요한 계획·근거·검증·기록을 보존하는가?
5. 단순한 업무에 불필요한 절차를 강요하지 않는가?
6. 권한을 선택·회수하고 가능한 감사와 되돌리기를 보존하는가?
7. 모델·Provider·프레임워크를 제품 정체성으로 승격하지 않는가?
8. 학습 결과가 실제 근거와 효과 평가를 가지는가?
9. Extension이 OS Core의 권한을 대체하지 않는가?
10. 기존 제품 기능을 일반적인 SaaS 화면으로 축소하지 않는가?

근거 없이 하나라도 실패하면 구현보다 제품 설계를 먼저 다시 검토합니다.

## 9. 제품 수용 기준

Massion의 첫 공개 릴리스는 다음 하나의 세로 흐름을 같은 후보 SHA에서 증명해야 합니다.

```text
사용자 Mission
→ Representative의 Work 생성
→ Workspace 지식과 근거 조사
→ 전략·Task·전문 실행 배정
→ Provider·모델 선택과 예산 계보
→ 병렬 실행·협업·사람 승인
→ 독립 검증과 Records
→ Growth 제안·평가·사람의 결정
→ 후속 Work 효과 확인 또는 Revert
```

이 흐름에는 다음 운영 경계도 포함됩니다.

- Provider가 없는 제한 모드와 인증 실패
- Work 취소, 차단, 재개와 비정상 종료 복구
- Workspace 신뢰와 파일 경계
- backup·restore와 재시작 보존
- 키보드, focus, 명암 대비와 스크린리더
- 서명·공증·Gatekeeper와 깨끗한 Mac 설치·제거

개별 화면, fixture, 패키지 테스트와 임시 빌드는 이 수용 기준을 대신하지 않습니다. 실행 결과는 후보 SHA에 결속된 evidence에서만 판정합니다.

## 10. 역사와 계승

Massion은 조직형 AI 운영을 독립 제품으로 만들기 위해 여러 실행 기반을 거쳤습니다.

- `claude-agent-bootstrap`: 대표·부서·전문가의 조직형 운영 가능성 확인
- TypeScript Jabtang: 영속 조직·Work·승인·기억과 Growth 확장
- Go·Eino 기반 Jabtang-go: OS Capability, 조직 그래프, 실행 그래프와 Runtime Truth 분리
- TypeScript·VoltAgent 기반 Massion: 실행 생태계를 교체하면서 Work·Assurance·Records·Extension·로컬 운영 계약 강화

이 계보는 특정 프레임워크를 고수하기 위한 것이 아닙니다. 사람이 지시하고 조직이 책임지며 검증된 경험만 다음 조직을 바꾼다는 제품 원칙을 보존하기 위한 역사입니다.
