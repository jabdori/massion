## 0. 이 문서에서 쓰는 말

이 문서는 내부 문서라 Work, Mission 같은 말을 씁니다. **사용자 화면에는 이 말이 나오지 않습니다.** '비서'도 이 문서의 설계 용어입니다. 화면에서는 비서를 이름으로만 부릅니다(§5.10).

| 화면에 보이는 말 | 안의 개념 |
|---|---|
| 이름(예: 하나). '비서'라고 부르지 않음 | 대표(Representative) |
| 일, 일 카드, 일 상세 | Work (Mission은 일의 목적으로 숨김) |
| 활동 | 맡긴 Work 목록(정하실 것 · 진행 중 · 최근) |
| 구성원 | 조직장·에이전트(Core Office, 실행자·검증자 포함) |
| 확인 | 독립 Assurance |
| 결과물, 서가 | 수용된 Record의 산출물과 그 모음 |
| 자세히, 자세히 보기 | 기준·검증·영수증·Record의 요약과 전체 |
| 예약 | 주기 실행 |
| 기억 · 배운 것 | 학습 기억, Growth 채택 |

## 1. 왜 바꿨나

### 1.1 v1 → v2

v1은 4영역 Work 화면을 제품의 중심에 두었습니다. 시장 조사와 소유자 논의 끝에 중심을 바꿨습니다. 최근 나온 비서형 제품(Claude Duet, Meta Muse, OpenAI dots, Grok Primary Bot)은 모두 사용자를 아는 비서 하나를 앞에 두고, 비서가 뒤에서 일을 나눕니다. Massion도 pi 시절부터 "모든 입력은 대표 하나로 들어온다"는 설계였습니다. 지금 재구축에서만 빠졌습니다. v2는 그 원칙으로 돌아갑니다.

### 1.2 v2 → v3

v2는 상단 탭 셋(대화 · 맡긴 일 · 결과물)과 늘 떠 있는 3단 패널로 그렸습니다. 2026-11-05에 소유자 Mac에서 실행 중인 ChatGPT · Claude 데스크톱 앱을 직접 조작하고 화면 구조를 읽었습니다. 두 앱 모두 고정 3단이나 상단 탭을 쓰지 않습니다. 가운데는 대화이고, 일이 생기면 그 옆에 작업 창이 열립니다. 목록은 사이드바 내용이 바뀌는 것으로, 서가 · 예약 · 설정은 레일에서 들어가는 전체 화면 페이지로 처리합니다.

소유자 피드백도 같은 방향이었습니다.

- 화면에서 '비서'라고 부르지 않습니다. 이름이 1인칭으로 말합니다.
- 설명 문장이 너무 많습니다. 다른 앱 화면에는 부제나 동작 해설이 없습니다.
- 첫 실행에 연결을 고르게 하지 않습니다. 로그인을 찾으면 바로 대화가 열립니다.

| 항목 | v1 | v2 | v3 |
|---|---|---|---|
| 첫 화면 | 서피스 레일 + 목록 + 협업 방 + 컨텍스트 | 이름 붙인 비서와의 대화 하나 | 대화 하나. 처음에는 레일과 대화만 |
| 일의 시작 | `새 업무` → 초안 카드 → 시작 | 비서에게 말하면 대화 속 일 카드가 생김 | v2와 같음 |
| 대화 | Work마다 협업 방 | 비서 대화 하나. '새 대화' 없음. 일마다 상세 | v2와 같음. 상세는 대화 옆 작업 창 |
| 탐색 | 레일 9개 서피스 | 탭 셋(대화 · 맡긴 일 · 결과물) + 설정 | 레일(하나 · 서가 · 예약 · 설정) + 사이드바 + 작업 창 |
| 4영역 Work 화면 | 제품의 중심 | 일 상세의 '자세히 보기' | 작업 창을 넓힌 상태 |
| 사람의 확인 | 결정 블록에서 승인/거절 | 사람은 두 가지만 결정. 확인은 다른 쪽이 함 | v2와 같음 |
| 검증 표시 | 참여자 줄에 증거 수준 | 정상은 조용히. 예외만 말함. 배지 없음 | v2와 같음 |
| 조직 | 실행자·검증자 2역할을 그대로 보임 | 화면에서 숨김. 제품 범위에서는 되살림 | v2와 같음 |
| 수신함 | 별도 서피스 | 맡긴 일 탭 맨 위 '정하실 것' | 사이드바 활동 보기 맨 위 '정하실 것' |
| 화면 문구 | 개발자 문구 | 비서, 설명 문장 | 이름과 라벨만(§5.10) |

## 2. 실측 마찰 (v1 §1, 근거로 유지)

2026-11-04에 첫 수직 흐름을 실제 모델과 브라우저 UI로 완주했습니다. 기능은 동작했습니다. 하지만 지금 화면으로는 매일 쓸 수 없었습니다.

| 실측한 마찰 | 원인 | 지금의 답 |
|---|---|---|
| Work 한 건에 Mission 작성, 권한 2개, Work 작성, 섹션 펼치기, 실행자·검증자·권한·상한 선택, 확인, 실행까지 10단계 이상 | 기능마다 양식이 하나씩 붙었고, 업무 기준으로 묶은 단계가 없음 | 말하기 한 번. 나머지는 비서와 기본값이 정함 |
| 한 페이지에 접힌 양식이 30여 개 | 정보 구조 없음 | 대화와 작업 창, 설정 페이지. 양식은 자세히 보기와 설정으로 |
| 실행 버튼이 접힌 `<details>` 안에 있음 | 자주 쓰는 동작이 가장 깊이 숨음 | 실행 버튼 없음. 일은 접수되면 바로 시작 |
| 권한 목록에 ID만 보임(수정됨) | 사람이 읽을 이름 규칙이 없었음 | 결정 카드는 늘 무엇·왜·되돌릴 수 있는지를 사람 말로 |
| 재시작하면 권한이 사라지고, 매번 모델을 직접 고름 | 권한이 세션 메모리에만 있음 | 영속 연결과 기본 실행 경로(구현 순서 1) |
| 기준을 사용자가 직접 문장으로 씀 | Mission 해석 지원 없음 | 비서가 기준을 세우고 일 상세에 보여 줌 |
| 마케팅 문구 히어로, 베이지 카드, 영어 개발자 문구 | 시각 기준 부재 | 디자인 시스템 유지 |

## 3. 사용자와 핵심 장면

- **사용자:** 자기 기기에서 Massion을 운영하는 한 명의 소유자. 개발자이지만 매번 내부 구조를 다루고 싶어 하지 않습니다.
- **핵심 장면:** 앱을 열면 어제 이어 쓰던 비서 대화가 그대로 있습니다. 비서가 먼저 말합니다. "맡기신 일 3건 중 2건 끝났고, 1건은 정하실 게 있습니다." 사용자는 한 문장으로 새 일을 맡기고, 노란 카드 하나에 답하고, 결과물을 엽니다. 확인은 안에서 끝났습니다. 사용자는 예외가 있을 때만 그 사실을 듣습니다.
- **다른 비서와 다른 점:** 다른 비서는 모델 하나가 알아서 합니다. Massion의 비서 뒤에는 책임지는 조직이 있습니다. 그래서 확인하지 않은 것을 했다고 말하지 않고, 결과를 모르면 모른다고 말하고, 정할 일은 묻습니다. 기능 이름이 아니라 비서의 말버릇으로 드러납니다.

## 4. 핵심 업무 (Jobs)

| # | 업무 | 시작 → 끝 | 목표 단계 수 | 현재 |
|---|---|---|---|---|
| J1 | **맡기기** | 비서에게 한 문장 → 대화 속 일 카드 → 바로 시작 | 1 (말하기). 꼭 물어야 할 때만 +1 | 일부: 메시지를 골라 Work 초안으로 바꾸는 경로는 있음. 비서가 답하고 Work를 만드는 경로는 없음 |
| J2 | **진행 보기** | 비서의 먼저 보고, 또는 일 카드를 눌러 작업 창의 일 상세 | 0 (보고를 읽음), 상세는 1 | 일부: 여러 Mission의 미해결 Work를 읽는 목록은 있음. 먼저 보고와 카드는 없음 |
| J3 | **결정하기** | 대화 속 결정 카드 → 동작 이름 버튼 | 1 | 일부: 소유자 양식만 있음(결과 모름 격리 · 만료 실행 종결은 예외 카드의 기반, Growth 채택·되돌리기). 결정 카드와 '다음부터 그냥 해'는 없음 |
| J4 | **못 고친 것 다루기** | 비서가 "조건 하나를 맞추지 못했어요" → 조건 바꿔 다시 맡기기 · 그만두기 · 확인 안 된 채로 두기 | 1. 고쳐서 통과하면 0 | 일부: 반려 이유와 소유자가 시작하는 수정 Work가 있음. 조직이 스스로 고쳐 다시 내는 경로는 없음 |
| J5 | **결과·근거 보기** | 일 카드 또는 서가 → 작업 창 미리보기 → 자세히 | 1, 근거까지 2 | 일부: 수용된 텍스트 결과와 Record를 정확히 읽는 경로가 있음. 텍스트만 됨 |
| J6 | **기억·개선** | 말한 것은 바로 기억 · 배운 것은 자동 반영 → 설정 > 기억에서 되돌리기 | 0. 되돌릴 때만 1 | 일부: 명시 기억 저장·중지·충돌·만료, 소유자 제안 Growth와 반올림 oracle 평가, 소유자 채택·되돌리기가 있음. 모델 제안과 자동 채택은 설계만 |
| J7 | **연결·예산** | 처음 실행 때 로그인 자동 감지 → 이후 기본 경로 | 로그인이 있으면 0, 없으면 1 | 일부: 호스트 manifest 아래 연결 · 권한 · 기본 실행 경로가 재시작 뒤에도 남음([default-route-and-persistent-connections](../architecture/default-route-and-persistent-connections.md), 서버 쪽, 픽스처 증거). 화면 조작, 로그인 자동 감지, 금액 한도는 없음 |

**원칙:** 매일 쓰는 경로(J1 → J2 → J3)는 첫 설정 뒤 **2단계 안에** 끝나야 합니다. v1에서 잰 10단계 이상과 같은 방법으로 다시 잽니다. 시장에 정량 채택 자료가 없으므로 이 측정이 화면의 근거입니다.

## 5. 화면 구조 (v3)

```
[레일] | [사이드바] | [가운데: 하나와의 대화] | [작업 창]

레일: 하나 · 서가 · 예약 · 설정 · 나(아래)
사이드바(숨길 수 있음):
  기본 = 대화 · 고정 · 최근 맡긴 일
  활동 보기 = 정하실 것 · 진행 중 · 최근
가운데: 날짜 구분선 · 브리핑 메시지, 일 카드, 'N분 동안 작업 >' 접힌 줄,
  결정 카드(노랑) · 예외 카드, 입력창 · 권한 칩
작업 창(필요할 때): 탭 · + · 닫기
  탭 = 일 상세 · 결과물 · 브라우저 · 파일 · 변경 사항
  둘 이상이면 가로 분할
서가 · 예약 · 설정 → 레일로 들어가는 전체 화면 페이지(대화를 대신함)
하나 이름 → 하나 프로필 팝오버
```

### 5.1 구조 구분

모든 화면은 같은 골격입니다. 바뀌는 것은 창 상태뿐입니다.

| 종류 | 무엇 | 언제 |
|---|---|---|
| 고정 | 왼쪽 레일(하나 · 서가 · 예약 · 설정, 맨 아래 내 아바타), 가운데 대화와 입력창 | 항상 |
| 사이드바 내용 전환 | 기본: 대화, 고정한 일, 최근 맡긴 일. 활동 보기: 정하실 것 · 진행 중 · 최근 | 토글. 새 창 없음 |
| 사이드바 숨기기 | 사이드바만 접고 레일은 남음. 대화는 가운데 정렬 | 토글 |
| 팝오버 | 하나 프로필, 내 아바타 메뉴, 입력창 @ 자동완성 | 누르면 뜨고 다시 누르면 닫힘 |
| 작업 창 | 대화 오른쪽. 0개 이상. 각 창은 탭(일 상세, 결과물 미리보기, 브라우저, 파일, 변경 사항) | 대화 안 카드 · 칩 · '자세히'를 누르거나, 하나가 열 때 |
| 전체 화면 페이지 | 서가, 예약, 설정 | 레일로 들어감. 대화를 대신함 |

- 기본 상태는 레일 + 사이드바 + 대화입니다. 처음 쓰는 사람에게는 레일과 대화만 보입니다.
- 창을 모두 닫으면 대화만 남습니다.

### 5.2 레일

- 하나: 대화로 돌아옵니다.
- 서가 · 예약 · 설정: 전체 화면 페이지로 들어갑니다(§5.8).
- 맨 아래 내 아바타: 내 메뉴 팝오버.
- 사용량, 모델 이름은 레일에 두지 않습니다.

### 5.3 사이드바

- **기본:** '대화' 한 줄, 고정한 일, 최근 맡긴 일(제목과 시각). 진행 중인 일은 빈 원, 결과 모름은 빨간 점으로 표시합니다.
- **활동 보기:** 사이드바 머리의 토글로 켭니다. 내용이 활동 목록으로 바뀝니다.
  - 묶음 순서: 정하실 것 → 진행 중 → 최근. 묶음 제목 옆에 개수.
  - 행: 굵은 제목, 결과 요약 두 줄, 맡은 구성원 아바타, 읽지 않음 파란 점. 열면 점이 사라집니다.
  - v2의 맡긴 일 탭과 수신함이 이 목록이 됩니다.
- **숨기기:** 대화 머리의 버튼으로 사이드바만 접습니다.
- 대화 목록과 '새 채팅'은 없습니다. 대화는 하나입니다.

### 5.4 가운데: 하나와의 대화

- 열면 같은 대화가 이어집니다. '새 대화' 버튼은 없습니다.
- 비서는 기억으로 개인화됩니다. 이름은 처음에 '하나'로 그렸습니다(§17).
- 비서가 먼저 보고합니다. 숫자는 실제 진행 상태에서만 셉니다. 아침 브리핑은 별도 피드가 아니라 대화 메시지 하나입니다(회색 카드). 날짜가 바뀌면 가운데 날짜 구분선을 둡니다. 브리핑은 예약 하나로 돌아가고, 빈도(끄기 · 낮게 · 높게)는 하나에게 말하거나 예약 페이지에서 바꿉니다.
- 말이 일이면 대표가 Work로 접수하고 대화에 **일 카드**를 올립니다. 카드는 제목, 상태, 단계 개수('만들기 1/1 · 확인 0/1'), '자세히'입니다. 진행은 같은 카드에서 바뀝니다. 질문이나 잡담은 그냥 답합니다.
- 과정은 **접힌 작업 줄** 하나로 둡니다(예: '2분 동안 작업 · 페이지 2개 읽음 >'). 펼치면 1인칭 진행 문장과 회색 한 줄 도구 호출이 번갈아 나옵니다.
- **결정 카드**(노랑)와 **예외 카드**(결과 모름 · 고치지 못함)는 대화 안에 둡니다(§5.6, §7).
- 누가 했는지는 기본으로 쓰지 않습니다. 사용자가 직접 부른 구성원의 말만 이름과 함께 붙습니다.
- 입력창: 자리표시는 '하나에게 말하기'. 아래에 권한 칩 하나('돈·보내기·지우기는 물어봄'). 입력창 위 상시 경고 배너는 두지 않습니다.

### 5.5 대화 옆 작업 창

- 대화의 카드 · 칩 · '자세히'를 누르면 대화 오른쪽에 열립니다. 대화는 계속 쓸 수 있습니다.
- 툴바 문법은 하나입니다: 탭 · `+` · 닫기. 넓히기는 일 상세 탭에서만 있습니다.
- 탭 종류: 일 상세, 결과물 미리보기(미리보기/원본), 브라우저, 파일, 변경 사항.
- 기본은 창 하나입니다. 둘 이상이면 가로로 나눕니다.
- **일 상세:** 위에 상태와 경과 시간, ■ 중지. 단계 줄(만들기 · 확인)과 흐름. 상태는 네 모양입니다: 진행 중, 고치지 못함, 결과 모름, 끝남. 끝남이면 남긴 결과물과 되돌리기, '서가에서 보기'.
- **넓히기 = 자세히 보기:** 일 상세 창을 넓히면 지금의 4영역 Work 화면(v1 A1~A4)이 됩니다. 사이드바는 접히고 대화는 좁게 남습니다. 만든 쪽 · 확인한 쪽 기록, 기준 · 기억 버전, 한 번만 보낸 실행, 기록과 지문, 흐름이 여기에만 보입니다. 모델 이름도 여기에만 있습니다. 좁히기로 돌아옵니다.
- **브라우저:** 하나와 소유자가 같이 봅니다. 하나 아바타가 페이지 위에 떠서 보는 곳을 가리킵니다. 주소창은 도메인만 보입니다. 규칙은 §11.
- 정본은 서가 한 곳이고, 대화와 일 상세는 서가로 연결만 합니다.

### 5.6 결정 카드

- 대화 안 노란 카드입니다. 대화 답장으로는 승인하지 않습니다.
- 담는 것: 무엇을, 어디로, 되돌릴 수 있는지, 감수할 것. 돈이면 금액과 만료, 브라우저 행동이면 작업 창에 그 페이지.
- 버튼: 동작 이름 버튼(예: '34,000원 결제') + '지금 말고'. 해당하면 '다음부터 이런 건 그냥 해'.
- 결정 결과는 그 자리에 남습니다. 활동 보기의 '정하실 것'에도 같은 일이 보입니다.
- 노랑은 결정 카드에만 씁니다.

### 5.7 팝오버

- **하나 프로필:** 대화 머리의 이름을 누르면 뜹니다. 이름, 상태와 마지막 활동(예: '일하는 중 · 마지막 활동 21:31'), 기억 · 구성원 바로가기, 기기, 최근 활동, 결과물(서가로 연결).
- **내 아바타 메뉴:** 레일 맨 아래.
- **@ 자동완성:** 입력창에서 `@`를 치면 구성원 목록이 뜹니다(§5.9).

### 5.8 전체 화면 페이지

레일로 들어가고 대화 자리를 대신합니다. 사이드바에는 그 페이지의 목록이 옵니다.

| 페이지 | 사이드바 | 본문 |
|---|---|---|
| 서가 | 전체 · 글 · 파일 · 이미지(개수), 최근 | 이름 · 만든 일 · 최근 표, 추천 · 즐겨찾기 · 내 것, 목록 · 격자 전환. 항목을 고르면 오른쪽에 미리보기/원본 |
| 예약 | 새 예약, 활성(이름 + 다음 실행 · 주기), 일시 정지됨 > | 다음 실행, 주기, 결과가 가는 곳(하나와의 대화), 맡길 말, 지난 실행. 켜기 토글과 '지금 실행' |
| 설정 | 일반 · 기억 · 구성원 · 기기 · 연결 · 개선 · 권한 | 둥근 카드 안 '제목 + 컨트롤' 행 |

설정 항목:

| 항목 | 내용 |
|---|---|
| 일반 | 이름, 브리핑 같은 기본값 |
| 기억 | 정하실 것, 내가 말한 것(버전, 지금 쓰는지), 배운 것(근거 표, 감수할 것, 나온 일), 바뀐 기록과 되돌리기. v2의 '비서가 아는 나' |
| 구성원 | 구성원 목록과 프로필(기억 · 기기 · 맡는 일 · 최근 활동), 구성원 추가 |
| 기기 | 이 Mac, 연결된 기기, 오프라인 기기와 다시 연결, 기기 연결 코드 |
| 연결 | 기본 경로(만들기 · 확인), 구독 로그인, 키. 확인 경로를 바꾸면 결정 카드 |
| 개선 | 대기 중인 것, 반영된 것과 되돌리기 |
| 권한 | 물어보는 것과 예외('다음부터 그냥 해'로 배운 허용). 지우면 다시 물음 |

| 기억 칸 | 내용 | 권위 |
|---|---|---|
| 내가 말한 것 | 명시 기억. 버전, 중지, 만료, 충돌 | 가장 높음 |
| 배운 것 | 학습 기억과 교훈. 근거, 적용 중인 버전, 확인된 효과, 되돌리기. 다음 일부터 적용 | 명시보다 낮음 |
| 구성원 기억 | 구성원별 홈 폴더의 기억. 설정 > 구성원 프로필에서 엶 | 구성원 범위 |

### 5.9 구성원

- 구성원 목록은 기본 화면에 두지 않습니다. 설정 > 구성원과 입력창 @ 자동완성으로만 드러납니다.
- 기본은 비서가 받습니다. @이름으로 부르면 그 구성원이 받습니다.

| 사용자가 한 일 | 누가 받나 | 어떻게 기록되나 |
|---|---|---|
| 그냥 말함 | 비서 | 비서 대화. 일이면 카드 |
| @Vega로 부름 | Vega | 같은 대화 줄기에 이름과 함께 답이 붙음 |
| 질문·조언 요청 | 그 구성원 | 그냥 대화. 실행 없음 |
| 진행 중인 일에 지시 | 그 구성원 | 그 Work의 방향 바꾸기(steer). 일 카드에 '방향 바뀜 · 이번 일만'. 감사 기록 |
| 새 일을 시킴 | 그 구성원 | Work로 접수. 활동에도 나타남 |
| 일시정지 · 중단 · 넘기기 | 정책 gate | 정책 gate가 권한을 검사하고 바로 처리. 새 구성원에게 넘기거나 권한을 넓힐 때만 결정 카드(§8). 감사 기록 |

- 구성원 프로필에는 기억 · 기기 · 맡는 일과 최근 활동만 둡니다. 구성원의 공간은 §12.

### 5.10 화면 문구 규칙

- **'비서'라고 부르지 않습니다.** 이름(예: 하나)이 1인칭으로 말합니다. "맡았어요. 답을 만들고 따로 확인한 뒤 알려 드릴게요." 기억은 '기억'이라고 부릅니다.
- **설명 문장을 두지 않습니다.** 부제, 동작 해설, 원칙 해설, 각주를 쓰지 않습니다. 라벨과 실제 내용만 남깁니다.
- **판정 기준:** "ChatGPT · Claude 화면에 그런 문장이 있나?" 없으면 지웁니다.
- 한국어 화면에 영어 진행형 문구를 섞지 않습니다.
- '다른 모델이 확인함' 같은 배지를 쓰지 않습니다. 읽지 않음 파란 점과 개수는 상태 표시라 씁니다.
- **첫 실행:** 로그인을 자동으로 찾습니다. 찾으면 바로 대화가 열리고 하나가 인사합니다. 찾지 못했을 때만 계속하기 버튼(Claude로 계속하기 / ChatGPT로 계속하기)과 작은 '다른 방법'을 보입니다. 연결을 고르는 단계는 없습니다.

## 6. 누가 확인하나

사람이 AI가 한 일을 매번 확인하면 사람이 병목이 됩니다. Massion은 "사람이 승인한다"가 아니라 "만든 쪽이 스스로 판정하지 않는다"를 지킵니다.

- **자기 판정 금지.** 만든 쪽과 확인하는 쪽은 다릅니다.
- **확인하는 쪽은 둘 중 하나입니다.** 호스트가 소유한 결정론적 평가기, 또는 만든 모델과 **다른 계열(개발사)** 의 모델입니다. 모델은 "좋아 보인다"가 아니라 실행 증거로 판단합니다. 증거가 없으면 통과가 아니라 "확인 못 함"입니다.
- **사람은 미리 승인하지 않습니다.** 사람은 §8의 순간에만 결정합니다.
- **자율 단계 설정은 만들지 않습니다.** 물어본 것은 '다음부터 그냥 해'로 배웁니다. 물어보는 횟수가 쓰면서 줄어듭니다.
- **신뢰는 기록으로 조절합니다.** 자동 반영했다가 나중에 되돌린 비율을 셉니다. 오르면 그 대상만 다시 꼼꼼히 봅니다.

현재: 실행자와 검증자는 다른 identity여야 하고 자기 검증은 domain에서 거부됩니다(구현됨). 계열(개발사) 구분은 아직 강제하지 않습니다. Growth 설계에 호스트 소유 계열 표가 제안되어 있습니다. 2026-11-04 실측은 Haiku 실행자와 Codex 검증자로 돌았습니다.

## 7. 정직성이 화면에 드러나는 방식 (예외만 말함)

독립 검증은 품질 공정이지 사용자가 읽을 문구가 아닙니다. '다른 모델이 확인함' 같은 배지는 쓰지 않습니다. 통과한 결과는 배지 없이 일 카드의 '자세히'로 근거를 엽니다.

| 안에서 일어난 일 | 사용자가 보는 것 | 시각 |
|---|---|---|
| 진행 중 | 일 카드 상태 한 줄, 사이드바의 빈 원 | 빈 원(`fg`) |
| 확인 통과 | 그냥 답이 옴. 배지 없음. '자세히' | 중립 글자(초록 없음) |
| 반려 후 고쳐서 통과 | 그냥 답이 옴. 일 상세에 "한 번 고쳤습니다" | 중립 |
| 고쳐도 기준을 못 맞춤 | "요청하신 조건 가운데 '정확히 한 줄'을 맞추지 못했습니다" + 조건 바꾸기 · 그만두기 · 확인 안 된 채로 두기 | `halt` 점 |
| 확인 못 함(검증 연결 실패 등) | 답에 한 줄: "확인하지 못한 결과입니다." | `halt` 점 |
| 결과 모름 | "보냈지만 응답을 받지 못했습니다. 중복될 수 있어 다시 보내지 않았습니다." + 예외 카드(종결 버튼) | `halt` 점 |
| 정할 일 | 결정 카드 | 노랑 |
| 종결(격리) | "종결됨 · 사유" | 중립 |
| 재시작 후 복원 | 보이지 않게 그대로 이어짐 | — |

'확인 안 된 채로 두기'는 수용이 아닙니다. 수용 Record를 만들지 않고, 서가에 "확인하지 못한 결과"로 표시합니다. 결과 모름은 자동으로 다시 보내지 않습니다. 반려 뒤 새 시도는 같은 요청을 다시 보내는 것이 아니므로 이 원칙과 충돌하지 않습니다. 다만 자동 새 시도의 횟수와 한도는 아직 정하지 않았습니다(§17).

## 8. 사람이 결정하는 순간

사람은 두 종류만 그 순간에 결정합니다.

**A. 되돌릴 수 없는 외부 행동**

1. 돈 쓰기: 결제, 구매, 유료 신청.
2. 내 이름으로 보내기: 메일, 메시지, 게시, 양식 제출. 사람 경계를 넘는 이동도 여기에 듭니다. 다른 사람이 볼 수 있는 공간으로 옮기면 묻습니다. 나만 보는 공간 안에서 옮기면 알리기만 합니다.
3. 지우기.
4. 새 구성원 들이기: 에이전트 추가, 사람 팀원 합류, 외부 에이전트에게 처음 맡기기, 확장 설치.

**B. 확인 규칙·권한 변경**

5. 확인 규칙: 평가기, 검증 규칙, 모델 계열 표.
6. 권한 넓히기: 도구 범위, 네트워크, 예산, 승인 범위. 권한이 늘어나는 확장 업데이트도 다시 묻습니다. 권한 안에서 좁히거나 정리하는 변경은 묻지 않습니다.

**예외 처리(미리 승인이 아니라 생긴 일에 답함. 결정 카드가 아니라 예외 카드)**

- 결과 모름 종결(격리), 만료된 실행 종결.
- 고치지 못한 결과: 조건 바꾸기 · 그만두기 · 확인 안 된 채로 두기(수용 아님).

**묻지 않고 알리기만 하는 것:** 개인 기억을 나만 보는 결과물에 옮겨 적을 때(사람 팀원이 볼 수 있는 곳이면 위 2번처럼 묻습니다), 자동 반영을 되돌렸을 때, Growth 한도에 닿았을 때.

그 밖의 일(조사, 정리, 초안, 계산, 내부 작업, 기억·지시문 개선)은 그냥 합니다.

## 9. 능동 협업

비서와 구성원이 먼저 움직입니다. Grok Bot과 Paperclip이 쓰는 장치를 Massion 불변식에 맞춥니다.

| 장치 | Massion에서 |
|---|---|
| 먼저 하기 | 비서가 기억 · 일정 · 지난 일을 보고 먼저 제안하거나 시작 |
| 스스로 맡기 | 대표가 배정하되 구성원이 "제가 맡겠습니다"로 가져갈 수 있음 |
| 한 명만 잡기 | 배정은 원자적으로 한 명. 진 쪽은 재시도하지 않음(한 번만 보내기와 같은 원칙) |
| 깨어나기 | 주기 실행과 이벤트 트리거(새 메일, 일정, 실패한 일) |
| 감시 | 기록 · 정책 책임이 멈춘 일과 반복 실패를 비서에게 보고 |
| 메시지 상한 | 구성원끼리 주고받는 메시지 수에 안에서 상한. 사용자에게는 보이지 않음 |

현재: 스케줄러, 주기 실행, 모델이 묻고 답하는 루프가 없습니다. 안에서 도는 것은 실행자·검증자 2역할뿐입니다. 대표 · 기록 · 정책 gate와 스케줄러가 먼저 필요합니다.

## 10. 조직과 OS

조직과 OS는 화면에서 숨기지만 제품 범위에서는 되살립니다. 겉을 대화로 바꾸면 사용자는 "알아서 해 주는 조직"을 기대하는데, 지금 안에서 도는 것은 2역할뿐이기 때문입니다.

- **Core Office:** Atlas · Lyra · Quill · Onyx · Vega · Iris · Cedar · Sage. 지금의 실행자는 Vega(실행 조정), 검증자는 Iris(독립 검증) 자리입니다.
- **되살리는 순서:** 대표(접수·응답) → 기록 → 정책 gate → 개선 → 확장(플러그인).
- **아카이브 코드:** 기준선으로 쓰지 않습니다. 요구사항 단위로 골라 다시 들입니다(ADR 0001).
- **사용자가 OS를 고치는 길:** 말로 요청하면 결정 카드로 확정합니다. 구성원 지도와 확장 화면은 설정 고급 화면에 둡니다.

## 11. 인앱 도구 우선순위

기본은 대화 속 카드입니다. 크게 보려면 대화 옆 **작업 창**에 탭으로 엽니다(§5.5).

| 순서 | 도구·뷰 | 이유 |
|---|---|---|
| 먼저 | 결과물 미리보기(문서 · HTML · PDF · 표 · 이미지) | 맡긴 사람이 가장 먼저 보는 것. 읽기 전용이라 위험이 낮음 |
| 먼저 | 대화 속 진행 카드 | 이미 있는 Work 기록을 대화로 끌어온 것. 새 상태가 필요 없음 |
| 다음 | 인앱 브라우저 | API가 없는 웹 일에 필요 |
| 다음 | 결정 카드(스크린샷 · 금액 · 만료) | 브라우저와 짝 |
| 코딩 일 | 파일 · 변경 · 터미널 | 코딩을 맡길 때만 |
| 나중 | 에이전트 컴퓨터 화면 | 클라우드 컴퓨터가 없음. 다시 보기는 단계별 스크린샷으로 |

브라우저 규칙:

- 읽기(이동 · 보기 · 스크롤)는 그냥 합니다.
- 제출 · 결제 · 전송과 그것을 일으키는 클릭은 **한 번만 보내는 실행**입니다. 어느 쪽인지 모르면 실행으로 봅니다.
- 제출 뒤 응답이 끊기면 결과 모름입니다. 다시 제출하지 않고 주문 내역이나 보낸 편지함을 다시 읽어 확인합니다. 그래도 모르면 묻습니다.
- 도구가 성공이라고 해도 별도 확인 읽기와 스크린샷으로 검증합니다.
- 비밀값은 비서가 볼 수 없는 입력 폼으로 받습니다.
- 외부 에이전트(Claude Code · Codex CLI)의 자체 브라우저는 계속 끕니다. 지금도 Codex는 `shell_tool`, `unified_exec`, `browser_use`, `in_app_browser`, `computer_use` 등 도구 기능을 끄고, Claude Code는 도구 없이 실행합니다(`src/cli-agent-providers.ts`). Massion 자체 브라우저만 엽니다.

확장은 도구와 뷰를 함께 기여합니다. 자리는 세 곳입니다: 대화 카드, 작업 창 탭, 일 상세 안 탭. 뷰는 격리된 화면에서 그리고 Massion을 거쳐서만 실행합니다.

## 12. 공간

| 공간 | 내용 |
|---|---|
| 구성원 개인 공간 | 홈 폴더(성격 · 명시 기억 · 학습 기억 · 스킬)는 늘 남음. 작업 폴더와 브라우저 프로필은 구성원마다 일 단위로 따로 둠. 일 단위 구성원은 일과 함께 끝나고 배운 것은 후보로만 남음 |
| 공통 공간 | 일마다 방(기본은 숨김, 대화에는 예외와 '방 열기'만)과 결과물 서가 |
| 사람 팀원 | 합류는 '새 구성원'이라 한 번 물음. 사람마다 비서 대화는 비공개. 팀원 누구나 조사·작성을 시킬 수 있지만 "내 이름으로 보내기"는 주인만 |
| 연결된 PC | 기본은 이 Mac. 비서가 데이터와 저장소를 보고 고름. 실행 위치 칩은 이 Mac이 아니거나 오프라인일 때만 보임. 칩을 바꾸면 새 일에만 적용. 호스트가 잠들면 실패가 아니라 일시정지 |
| Reason 기기 | Reason으로 연결된 기기는 소유자 본인 것이라도 외부 구성원으로 다룸. 결과는 확인 전까지 모름 |
| 기억 | 설정 > 기억(§5.8) |

사람 경계를 넘는 이동만 묻습니다. 다른 사람이 볼 수 있는 공간으로 옮기면 묻습니다. 나만 보는 공간 안에서 옮기면 알리기만 합니다. 실행 권한(폴더 · 호스트 · 브라우저)과 자기수정 권한(기억 · 지시 채택)은 두 축으로 따로 둡니다. 구성원의 정체성과 기억은 실행 공간이 바뀌어도 남습니다(scope.md 불변식).

## 13. 외부 에이전트

다른 서비스의 에이전트는 Massion 조직의 정식 구성원이 아니라 계약직처럼 다룹니다. 특정 네트워크에 묶지 않고 **외부 구성원 어댑터** 하나로 감쌉니다. 프로바이더를 연결 방식별 factory로 나눈 지금 구조와 같은 방식입니다.

- 첫 어댑터: Reason Network(로컬 코딩 에이전트와 호스팅 비서를 잇는 네트워크).
- 두 번째 어댑터: 표준 A2A.

조건:

1. **도착은 처리가 아닙니다.** 답이 올 때까지 결과 모름입니다.
2. **같은 요청을 두 번 보내지 않습니다.** 실행 하나마다 멱등 키를 고정합니다. 붙이기 전에 실제로 한 번만 도착하는지 시험합니다.
3. **외부 결과도 검증합니다.** 같은 독립 확인을 거칩니다. 화면은 여전히 예외만 말합니다.
4. **받은 글은 데이터입니다.** 지시로 읽지 않습니다.
5. **신뢰 범위를 좁게 시작합니다.** 처음에는 사용자 본인 머신의 에이전트만. 본인 머신이라도 Reason으로 연결되면 외부 구성원이고, 결과는 확인 전까지 모름입니다. 팀원이나 호스팅 봇에게 처음 맡길 때 한 번 묻고, 그다음은 기억합니다.

현재: INT-01은 연결된 제품 경로가 없습니다(requirements.md).

## 14. 코딩 Work, Growth, 구현 순서

### 14.1 코딩 Work (pstack에서 가져옴)

- 큰 코딩 일은 혼자 착지·검증할 수 있는 하위 Work로 나눕니다. 하위 Work마다 기준과 검증 하나.
- 스택은 Work 의존입니다. 부모 Work의 수락된 산출물(커밋)이 자식 Work의 고정 입력입니다.
- 아래부터, 검증된 구간만 자동으로 착지합니다. 첫 미검증 지점에서 멈춥니다.
- 병합·push는 다시 읽어 확정합니다. 되읽기에 실패하면 결과 모름이고 다시 보내지 않습니다.
- 루프 한 바퀴 = 변경 하나 · 검증 하나 · 기록 한 줄. 버린 시도도 Record에 남깁니다.
- 반복되는 교정은 에이전트가 가장 강한 층(구조 → 정적 검사 → 지침 → 문서)에 고정합니다. 지침 · 문서 층과 규칙을 좁히는 변경은 다른 계열 모델의 확인을 거쳐 자동 반영하고, 버전을 남기고, 되돌릴 수 있습니다. 정적 검사 · 검증 규칙 · 평가기를 바꾸는 고정은 확인 규칙 변경이라 결정 카드(§8 B)로 묻습니다.

현재 기반: 소유자가 정한 순서로 Work를 차례로 돌리는 경로(run sequence)와, 앞 Work의 수락된 Record를 요구하는 선행 조건(prerequisites)이 있습니다. 코드 변경·병합·push 경로는 없습니다.

### 14.2 Growth

설계는 [growth-reflection-and-model-proposals.md](../architecture/growth-reflection-and-model-proposals.md)를 따릅니다. 일곱 단계 가운데 1~2단계를 설계했습니다.

1. 실행 기록(reflection trail): 끝난 Work 하나를 결정론적으로 읽기 전용 투영. 행동은 그대로.
2. 모델이 제안하는 기억 후보: 측정된 개선이 있으면 소유자를 기다리지 않고 자동 채택. 되돌린 비율로 보정(calibration). 명시 기억을 대체하는 후보는 자동 채택하지 않고 결정 카드로 묻습니다. 기본이 자동이라는 것은 ADR 0002의 결정이고, 설계 문서도 이에 맞춰 자동/검토 선택을 없앴습니다.
3~7. 평가기 추가, 효과 관찰, 프롬프트·도구 안내 대상, 교훈 라이브러리, 정책·조직 대상.

화면: 설정은 없습니다. 정상적으로 자동 채택된 것은 대화에 올리지 않고 설정 > 기억의 '배운 것'에만 남깁니다. 대화에는 예외만 올립니다: 되돌림, 한도 도달, 명시 기억을 대체하는 후보. 묻는 것은 확인 규칙 · 권한을 바꿀 때뿐이고, 결정 카드로 묻습니다.

현재: 설계 문서 상태는 "proposed design, not implemented"입니다. 구현된 것은 소유자 제안, 호스트 반올림 oracle 평가, 소유자 채택·되돌리기입니다.

### 14.3 구현 순서

도그푸딩 걸림돌과 같은 순서입니다.

1. **기본 실행 경로와 영속 연결.** 재시작 뒤에도 권한과 기본 실행자·검증자가 남아야 매일 쓸 수 있습니다.
2. **비서 대화.** 대표가 대화하고, 일이면 Work를 만듭니다.
3. **Growth 1단계 실행 기록.**

## 17. 남은 질문

1. 반려 뒤 조직이 스스로 고쳐 다시 내는 횟수와 한도는 얼마인가? 이 정책은 불변식 문서에 들어가야 합니다.
2. 영속 권한의 모양은 무엇인가? '다음부터 그냥 해'로 배운 허용과 지금의 Mission 범위 권한(scoped grant)을 같은 것으로 볼 것인가?
3. 명시 기억을 대체하는 후보를 결정 카드로 묻는 것을 '소유자 지시를 바꾸는 일'로 보는 해석이 맞는가? 지금 문서는 그렇게 정했습니다.
4. 모델 계열 표는 누가 처음 채우는가? 표에 없는 모델은 같은 계열로 봅니다. 그러면 처음에는 모델 검증자가 거의 쓰이지 않을 수 있습니다.
5. 대표가 "이건 일이다"라고 판단하는 기준은 무엇이고, 그 판단은 누가 확인하는가? 일로 잘못 접수하면 비용이 생기고, 놓치면 책임이 사라집니다.
6. 기준 초안은 대표가 씁니다. 사용자는 일 상세에서만 봅니다. 기준이 틀렸을 때 고치는 길은 대화로 충분한가?
7. 구성원 간 메시지 상한은 얼마인가? Reason Network는 에이전트 쌍마다 10분에 12건을 씁니다.
8. 같은 비서를 Slack · 텔레그램 · 메시지 앱에서 부르는 것은 이번 범위에서 뺍니다. 자리를 비웠을 때 결정 카드를 받을 곳은 그동안 무엇인가?
9. 아침 브리핑의 '의미 있게 새로운 것'은 어떻게 정하는가?
10. **작업 창 분할 규칙.** 새 탭은 지금 창에 붙는가, 새 창으로 나뉘는가? 창은 최대 몇 개인가? 결정 카드의 근거 페이지가 열려 있을 때 다른 일의 상세를 열면 어떻게 되는가?
11. **예약의 범위.** 예약은 소유자만 만드는가, 하나가 제안해서 만들 수도 있는가? 결과는 늘 하나와의 대화로만 가는가? 예약 실행이 돈 쓰기나 보내기에 닿으면 그때마다 결정 카드인가?
12. **활동 정렬 기준.** '최근'은 끝난 시각순인가, 읽지 않음이 먼저인가? 고정한 일과 활동 목록은 어떻게 겹치는가?
13. **비서 이름.** 첫 실행에서 이름 정하기 단계를 뺐습니다. 첫 실행 뒤 이름을 정하라고 언제 권하는가? 바꾸는 곳은 설정 > 일반입니다.
