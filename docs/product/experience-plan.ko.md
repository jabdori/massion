## 0. 이 문서에서 쓰는 말

이 문서는 내부 문서라 Work, Mission 같은 말을 씁니다. **사용자 화면에는 이 말이 나오지 않습니다.** '비서'도 이 문서의 설계 용어입니다. 화면에서는 비서를 이름으로만 부릅니다(§5.10).

| 화면에 보이는 말 | 안의 개념 |
|---|---|
| 이름(예: 하나). '비서'라고 부르지 않음 | 대표(Representative) |
| 일, 일 카드, 일 상세 | Work (Mission은 일의 목적으로 숨김) |
| 활동 | 하나와 모든 구성원의 Work 목록(우선순위 정렬) |
| 구성원 | 소유자가 들이고 이름 붙인 구성원(ADR 0003). 일마다 생기는 팀장 · 팀원은 화면에 없고, 일꾼은 역할 칩으로만 보임 |
| 업무 방 | 한 Work의 협업 방(참가자, 진행표, 확인 줄) |
| 모델 그룹 | 역할 설명이 붙은 모델 묶음 |
| 앱 | 확장(extension) |
| 확인 | 독립 Assurance |
| 결과물 | 수용된 Record의 산출물과 그 모음(v3의 '서가') |
| 자세히, 자세히 보기 | 기준·검증·영수증·Record의 요약과 전체 |
| 예약 | 주기 실행 |
| 기억 · 배운 것 | 학습 기억, Growth 채택 |

## 1. 왜 바꿨나

### 1.1 v1 → v2

v1은 4영역 Work 화면을 제품의 중심에 두었습니다. 시장 조사와 소유자 논의 끝에 중심을 바꿨습니다. 최근 나온 비서형 제품(Claude Duet, Meta Muse, OpenAI dots, Grok Primary Bot)은 모두 사용자를 아는 비서 하나를 앞에 두고, 비서가 뒤에서 일을 나눕니다. Massion도 pi 시절부터 "모든 입력은 대표 하나로 들어온다"는 설계였습니다. 지금 재구축에서만 빠졌습니다. v2는 그 원칙으로 돌아갑니다.

### 1.2 v2 → v3

v2는 상단 탭 셋(대화 · 맡긴 일 · 결과물)과 늘 떠 있는 3단 패널로 그렸습니다. 2026-11-05에 소유자 Mac에서 실행 중인 ChatGPT · Claude 데스크톱 앱을 직접 조작하고 화면 구조를 읽었습니다. 두 앱 모두 고정 3단이나 상단 탭을 쓰지 않습니다. 가운데는 대화이고, 일이 생기면 그 옆에 작업 창이 열립니다. 목록은 사이드바 내용이 바뀌는 것으로, 서가 · 예약 · 설정은 레일에서 들어가는 전체 화면 페이지로 처리합니다.

소유자 피드백도 같은 방향이었습니다.

- 화면에서 '비서'라고 부르지 않습니다. 이름이 1인칭으로 말합니다.
- 설명 문장이 너무 많습니다. 다른 앱 화면에는 부제나 동작 해설이 없습니다.
- 첫 실행에 연결을 고르게 하지 않습니다. 로그인을 찾으면 바로 대화가 열립니다.

| 항목 | v1 | v2 | v3 |
|---|---|---|---|
| 첫 화면 | 서피스 레일 + 목록 + 협업 방 + 컨텍스트 | 이름 붙인 비서와의 대화 하나 | 대화 하나. 처음에는 레일과 대화만 |
| 일의 시작 | `새 업무` → 초안 카드 → 시작 | 비서에게 말하면 대화 속 일 카드가 생김 | v2와 같음 |
| 대화 | Work마다 협업 방 | 비서 대화 하나. '새 대화' 없음. 일마다 상세 | v2와 같음. 상세는 대화 옆 작업 창 |
| 탐색 | 레일 9개 서피스 | 탭 셋(대화 · 맡긴 일 · 결과물) + 설정 | 레일(하나 · 서가 · 예약 · 설정) + 사이드바 + 작업 창 |
| 4영역 Work 화면 | 제품의 중심 | 일 상세의 '자세히 보기' | 작업 창을 넓힌 상태 |
| 사람의 확인 | 결정 블록에서 승인/거절 | 사람은 두 가지만 결정. 확인은 다른 쪽이 함 | v2와 같음 |
| 검증 표시 | 참여자 줄에 증거 수준 | 정상은 조용히. 예외만 말함. 배지 없음 | v2와 같음 |
| 조직 | 실행자·검증자 2역할을 그대로 보임 | 화면에서 숨김. 제품 범위에서는 되살림 | v2와 같음 |
| 수신함 | 별도 서피스 | 맡긴 일 탭 맨 위 '정하실 것' | 사이드바 활동 보기 맨 위 '정하실 것' |
| 화면 문구 | 개발자 문구 | 비서, 설명 문장 | 이름과 라벨만(§5.10) |

## 2. 실측 마찰 (v1 §1, 근거로 유지)

2026-11-04에 첫 수직 흐름을 실제 모델과 브라우저 UI로 완주했습니다. 기능은 동작했습니다. 하지만 지금 화면으로는 매일 쓸 수 없었습니다.

| 실측한 마찰 | 원인 | 지금의 답 |
|---|---|---|
| Work 한 건에 Mission 작성, 권한 2개, Work 작성, 섹션 펼치기, 실행자·검증자·권한·상한 선택, 확인, 실행까지 10단계 이상 | 기능마다 양식이 하나씩 붙었고, 업무 기준으로 묶은 단계가 없음 | 말하기 한 번. 나머지는 비서와 기본값이 정함 |
| 한 페이지에 접힌 양식이 30여 개 | 정보 구조 없음 | 대화와 작업 창, 설정 페이지. 양식은 자세히 보기와 설정으로 |
| 실행 버튼이 접힌 `<details>` 안에 있음 | 자주 쓰는 동작이 가장 깊이 숨음 | 실행 버튼 없음. 일은 접수되면 바로 시작 |
| 권한 목록에 ID만 보임(수정됨) | 사람이 읽을 이름 규칙이 없었음 | 결정 카드는 늘 무엇·왜·되돌릴 수 있는지를 사람 말로 |
| 재시작하면 권한이 사라지고, 매번 모델을 직접 고름 | 권한이 세션 메모리에만 있음 | 영속 연결과 기본 실행 경로(구현 순서 1) |
| 기준을 사용자가 직접 문장으로 씀 | Mission 해석 지원 없음 | 비서가 기준을 세우고 일 상세에 보여 줌 |
| 마케팅 문구 히어로, 베이지 카드, 영어 개발자 문구 | 시각 기준 부재 | 디자인 시스템 유지 |

## 3. 사용자와 핵심 장면

- **사용자:** 자기 기기에서 Massion을 운영하는 한 명의 소유자. 개발자이지만 매번 내부 구조를 다루고 싶어 하지 않습니다.
- **핵심 장면:** 앱을 열면 어제 이어 쓰던 비서 대화가 그대로 있습니다. 비서가 먼저 말합니다. "맡기신 일 3건 중 2건 끝났고, 1건은 정하실 게 있습니다." 사용자는 한 문장으로 새 일을 맡기고, 노란 카드 하나에 답하고, 결과물을 엽니다. 확인은 안에서 끝났습니다. 사용자는 예외가 있을 때만 그 사실을 듣습니다.
- **다른 비서와 다른 점:** 다른 비서는 모델 하나가 알아서 합니다. Massion의 비서 뒤에는 책임지는 조직이 있습니다. 그래서 확인하지 않은 것을 했다고 말하지 않고, 결과를 모르면 모른다고 말하고, 정할 일은 묻습니다. 기능 이름이 아니라 비서의 말버릇으로 드러납니다.

## 4. 핵심 업무 (Jobs)

| # | 업무 | 시작 → 끝 | 목표 단계 수 | 현재 |
|---|---|---|---|---|
| J1 | **맡기기** | 비서에게 한 문장 → 대화 속 일 카드 → 바로 시작 | 1 (말하기). 꼭 물어야 할 때만 +1 | 일부: 메시지를 골라 Work 초안으로 바꾸는 경로는 있음. 비서가 답하고 Work를 만드는 경로는 없음 |
| J2 | **진행 보기** | 비서의 먼저 보고, 또는 일 카드를 눌러 작업 창의 일 상세 | 0 (보고를 읽음), 상세는 1 | 일부: 여러 Mission의 미해결 Work를 읽는 목록은 있음. 먼저 보고와 카드는 없음 |
| J3 | **결정하기** | 대화 속 결정 카드 → 동작 이름 버튼 | 1 | 일부: 소유자 양식만 있음(결과 모름 격리 · 만료 실행 종결은 예외 카드의 기반, Growth 채택·되돌리기). 결정 카드와 '다음부터 그냥 해'는 없음 |
| J4 | **못 고친 것 다루기** | 비서가 "조건 하나를 맞추지 못했어요" → 조건 바꿔 다시 맡기기 · 그만두기 · 확인 안 된 채로 두기 | 1. 고쳐서 통과하면 0 | 일부: 반려 이유와 소유자가 시작하는 수정 Work가 있음. 조직이 스스로 고쳐 다시 내는 경로는 없음 |
| J5 | **결과·근거 보기** | 일 카드 또는 서가 → 작업 창 미리보기 → 자세히 | 1, 근거까지 2 | 일부: 수용된 텍스트 결과와 Record를 정확히 읽는 경로가 있음. 텍스트만 됨 |
| J6 | **기억·개선** | 말한 것은 바로 기억 · 배운 것은 자동 반영 → 설정 > 기억에서 되돌리기 | 0. 되돌릴 때만 1 | 일부: 명시 기억 저장·중지·충돌·만료, 소유자 제안 Growth와 반올림 oracle 평가, 소유자 채택·되돌리기가 있음. 모델 제안과 자동 채택은 설계만 |
| J7 | **연결·예산** | 처음 실행 때 로그인 자동 감지 → 이후 기본 경로 | 로그인이 있으면 0, 없으면 1 | 일부: 호스트 manifest 아래 연결 · 권한 · 기본 실행 경로가 재시작 뒤에도 남음([default-route-and-persistent-connections](../architecture/default-route-and-persistent-connections.md), 서버 쪽, 픽스처 증거). 화면 조작, 로그인 자동 감지, 금액 한도는 없음 |

**원칙:** 매일 쓰는 경로(J1 → J2 → J3)는 첫 설정 뒤 **2단계 안에** 끝나야 합니다. v1에서 잰 10단계 이상과 같은 방법으로 다시 잽니다. 시장에 정량 채택 자료가 없으므로 이 측정이 화면의 근거입니다.

## 5. 화면 구조 (v3.1)

```
[레일] | [사이드바] | [가운데: 대화] | [작업 창]

레일: 하나 · 결과물 · 예약 · 설치한 앱 · 나(아래)
사이드바(숨길 수 있음):
  기본 = 하나 · 구성원 · 일하는 동안 그 사람 아래 일 줄
  활동 보기 = 우선순위로 정렬한 목록 하나
가운데: 하나 또는 구성원과의 대화. 날짜 구분선 · 브리핑 메시지, 바로 답,
  'N분 동안 작업 ›' 접힌 줄, 일 카드, 결정 카드(노랑) · 예외 카드,
  회색 시스템 줄, 입력창 · '기본 권한' 칩
작업 창(필요할 때): 탭 · 넓히기 · 닫기
  탭 = 업무 방(탭 이름은 일 이름) · 결과물 미리보기 · 브라우저 · 앱 탭(예: PR #84)
결과물 · 예약 · 앱 페이지 → 레일로 들어가는 전체 화면 페이지(대화를 대신함)
설정 → '나' 메뉴
이름 → 프로필 팝오버
```

### 5.1 구조 구분

모든 화면은 같은 골격입니다. 바뀌는 것은 창 상태뿐입니다.

| 종류 | 무엇 | 언제 |
|---|---|---|
| 고정 | 왼쪽 레일(하나 · 결과물 · 예약 · 설치한 앱, 맨 아래 나), 가운데 대화와 입력창 | 항상 |
| 사이드바 내용 전환 | 기본: 하나 · 구성원 · 일 줄. 활동 보기: 우선순위 목록 | 토글. 새 창 없음 |
| 사이드바 숨기기 | 사이드바만 접고 레일은 남음. 대화는 가운데 정렬 | 토글 |
| 팝오버 | 프로필(하나 · 구성원), 나 메뉴, 입력창 @ 자동완성, '기본 권한' 메뉴 | 누르면 뜨고 다시 누르면 닫힘 |
| 작업 창 | 대화 오른쪽. 탭(업무 방, 결과물 미리보기, 브라우저, 앱 탭) | 일 카드 · 일 줄 · 활동 행 · 접힌 작업 줄을 누르거나, 하나가 열 때 |
| 전체 화면 페이지 | 결과물, 예약, 앱 페이지, 설정 | 레일 또는 나 메뉴로 들어감. 대화를 대신함 |

- 처음 쓰는 사람에게는 레일(하나 · 결과물 · 예약)과 하나와의 대화만 보입니다. 설치한 앱과 구성원은 생긴 뒤에만 보입니다.
- 창을 모두 닫으면 대화만 남습니다.

### 5.2 레일

- 하나: 하나와의 대화로 돌아옵니다.
- 결과물 · 예약: 전체 화면 페이지로 들어갑니다(§5.8).
- 설치한 앱: 기본 아이콘 아래에 앱 아이콘(예: GitHub)이 붙습니다. 누르면 그 앱의 페이지가 열립니다.
- 맨 아래 나: 메뉴(설정 ⌘, · 도움말 · 로그아웃). 설정은 여기서 들어가고 '일반'에서 시작합니다. 레일에 설정 아이콘은 없습니다.
- 사용량, 모델 이름은 레일에 두지 않습니다.

### 5.3 사이드바

- **기본:** 맨 위 하나, 그 아래 소유자가 들인 구성원. 이름과 아바타만 보입니다. 아바타가 상태를 보여 줍니다(작업 중 점 세 개, 읽지 않음 파란 점). 구성원이 0명이면 하나만 있습니다.
- **일 줄:** 그 사람이 일하는 동안에만 그 사람 아래에 펼쳐집니다. 일 이름만 쓰고 상태는 오른쪽 상태 원으로 보입니다. 누르면 맡은 사람의 대화가 가운데에, 그 일의 업무 방이 작업 창에 열립니다.
- '고정', '최근 맡긴 일', 대화 목록, '새 채팅'은 없습니다.
- **활동 보기:** 사이드바 머리의 토글로 켭니다.
  - 묶음 제목과 개수 없이 목록 하나입니다. 머리의 정렬 메뉴에서 우선순위 · 최근을 고릅니다.
  - 우선순위 순서: 결정 대기 → 예외 → 실행 중 → 완료.
  - 행: 굵은 일 이름, 회색 해요체 요약 두 줄, 맡은 사람 아바타, 읽지 않음 파란 점. 결정을 기다리는 행은 요약이 질문입니다('…바꿀까요?').
  - 하나와 모든 구성원의 일이 들어갑니다. 행을 누르면 일 줄과 같은 곳으로 갑니다.
  - 일이 없으면 정렬 머리도 없습니다.
- **숨기기:** 대화 머리의 버튼으로 사이드바만 접습니다.

### 5.4 가운데: 대화

- 하나와의 대화 하나, 구성원마다 1:1 대화 하나입니다. '새 대화' 버튼은 없습니다.
- 대화 머리에는 이름만 있습니다. 누르면 프로필 팝오버가 뜹니다.
- 하나가 먼저 보고합니다. 아침 브리핑은 대화 안 회색 카드 메시지 하나입니다('아침 브리핑 | 11월 5일 (목) 오전 8:00'). 불릿마다 일 이름이 링크이고, 누르면 그 일의 대화와 업무 방이 열립니다. 숫자는 실제 진행 상태에서만 셉니다. 날짜가 바뀌면 가운데 날짜 구분선을 둡니다.
- **바로 답하기와 일로 넘기기** ([ADR 0003](../architecture/decisions/0003-members-internal-teams-model-groups-and-apps.md) §6):

| 바로 답함 (대화 안에서 끝냄) | 일로 넘김 (일 카드 + 업무 방) |
|---|---|
| 질문, 설명, 짧은 계산, 요약, 번역, 초안 한 번 | 여러 단계이거나, 소유자가 대화를 떠나 있을 만큼 오래 걸리는 일 |
| 결과가 대화 답 그 자체인 것 | 파일 · 문서 · 코드 같은 결과물이 남는 일 |
| 외부에 아무 영향이 없는 것 | 외부 도구 · 사이트 · 앱을 쓰는 일, 보내기 · 결제처럼 효과가 있는 일 |
| | 구성원이나 팀이 붙는 일, 예약으로 반복하는 일 |
| | 소유자가 "제대로 확인해서" 같은 조건을 붙인 일 |

- 바로 받은 답은 대화 답이지 수락된 결과가 아닙니다. 독립 확인, 일 카드, 업무 방이 붙지 않습니다. 소유자가 "확인해 줘"라고 하면 그때 일로 넘어갑니다.
- 한 단계로 혼자 끝나는 작은 일은 접힌 '4분 동안 작업 ›' 줄과 결과만 보입니다. 일 카드와 업무 방은 여러 단계이거나 참가자가 여럿일 때만 나옵니다.
- **일 카드:** 일 이름, 상태와 경과 시간, 맡은 사람 아바타, 역할 칩(예: 조사 · 분류 · 요약 · 확인), 단계 카운터('3/5'), 한 줄 진행. '자세히'는 없습니다. 입구는 카드 클릭과 접힌 작업 줄 둘입니다.
- **회색 시스템 줄:** 쌍점 형식입니다. '하나가 넘김: 이탈 원인 조사 · 09:40', '방향 바꿈: 이탈 원인 조사', '기억 후보: 표 금액은 원 단위 [남기기] [지우기]', '나중에: GitHub 앱 [다시 묻기]', 'GitHub 앱 설치됨 [제거]'. '하나가 넘김'은 하나가 구성원에게 넘긴 일에만 붙습니다.
- 결정 카드와 예외 카드는 생긴 시각 자리에 둡니다(§5.6).
- 입력창: 자리표시는 '하나에게 메시지 보내기'(구성원 대화는 이름만 바뀜). 아래에 '기본 권한 ▾' 칩 하나. 메뉴에서 설정 > 권한으로 갑니다.

### 5.5 대화 옆 작업 창

- 대화의 일 카드 · 접힌 줄을 누르거나 사이드바 일 줄 · 활동 행을 누르면 대화 오른쪽에 열립니다. 대화는 계속 쓸 수 있습니다.
- 툴바: 탭 · 넓히기 · 닫기. 탭 이름은 내용 이름입니다(일 이름, 'PR #84').
- **업무 방(협업 방):** 일 하나의 방입니다.
  - 참가자: 맡은 구성원 이름, 역할 칩(이름 없는 일꾼), 맨 끝 '확인'.
  - 진행표: 구성원의 절차를 이번 일에 맞춰 펼친 단계. 건너뛴 단계는 '건너뜀 · 이유'로 보입니다.
  - 참가자끼리 주고받은 말.
  - 맨 아래 확인 줄. 누가 확인했는지는 '자세히' 안에만 있습니다.
  - ■ 중지.
- 상태는 실행 중 · 확인 대기 · 실패 · 결과 모름 · 완료입니다. 창에는 상태 줄만 두고, 예외 버튼은 대화의 예외 카드에만 둡니다.
- 완료: 결과물 카드에 [실행 취소] [결과물 보기].
- **넓히기 = 자세히 보기:** 업무 방을 넓히면 4영역 Work 화면(v1 A1~A4)이 됩니다. 사이드바는 접히고 대화는 좁게 남습니다. 만든 쪽 · 확인한 쪽 기록, 기준 버전 · 기준 내용, 전송 1회 보장, 기록과 해시, 흐름, 모델 이름이 여기에만 보입니다.
- **결과물 미리보기:** 결과물 페이지에서 행을 누르면 그 결과물을 만든 대화와 반반으로 열립니다.
- **브라우저:** 하나와 소유자가 같이 봅니다. 하나 아바타가 페이지 위에 떠서 보는 곳을 가리킵니다. 주소창은 도메인만 보입니다. 규칙은 §11.
- **앱 탭:** 앱이 업무 방에 더하는 탭입니다(예: GitHub 앱의 PR 탭).
- 정본은 결과물 한 곳이고, 대화와 업무 방은 결과물로 연결만 합니다.

### 5.6 결정 카드와 예외 카드

- **결정 카드**는 대화 안 노란 카드입니다. 대화 답장으로는 승인하지 않습니다. 노랑은 결정 카드에만 씁니다.
- 머리에는 질문 제목과 시각만 있습니다. 범주 라벨은 없습니다.
- 담는 것: 무엇을, 어디로, 취소할 수 있는지, 주의. 돈이면 상품 · 판매처 · 금액 · 결제 기한, 브라우저 행동이면 작업 창에 그 페이지.
- 버튼: 동작 이름 버튼(예: [결제], [바꾸기], [구성원 추가], [설치]) + [나중에]. [나중에]는 회색 줄 '나중에: … [다시 묻기]'로 남습니다. 정한 뒤에는 '… 변경됨 [되돌리기]' 줄이 남습니다.
- 카드에는 '다음부터 그냥 해'가 없습니다. 묻지 않을 일은 설정 > 권한의 두 칸 규칙(항상 묻기 / 묻지 않고 허용)에서 정합니다(§17).
- 쓰는 곳: 돈, 보내기, 지우기, 새 구성원, 앱 설치와 권한 넓히기, 확인 규칙 변경(§8).
- **예외 카드**는 모든 예외에 같은 모양입니다: '● 일 이름 · 상태 시각 · 한 줄 사실' + [다시 시도] [닫기]. 조건을 바꾸는 것은 [다시 시도] 뒤 대화에서 합니다. 세부는 업무 방에만 둡니다.

### 5.7 팝오버

- **프로필 팝오버:** 대화 머리나 사이드바의 이름을 누르면 뜹니다. 하나와 구성원이 같은 모양입니다. 이름, 상태('작업 중 · 일 2개' 또는 '마지막 활성 21:31'), 최근 활동(상태 원), '더 보기'. 하나는 기억 · 구성원 · 기기(이 Mac · 준비됨)도 보입니다. '더 보기'는 설정 > 구성원의 그 사람 페이지로 갑니다.
- **나 메뉴:** 레일 맨 아래. 설정 ⌘, · 도움말 · 로그아웃.
- **@ 자동완성:** 입력창에서 `@`를 치면 구성원 목록이 뜹니다. 맨 아래 '구성원 관리'는 설정 > 구성원으로 갑니다.

### 5.8 전체 화면 페이지

레일이나 나 메뉴로 들어가고 대화 자리를 대신합니다. 사이드바에는 그 페이지의 목록이 옵니다.

| 페이지 | 사이드바 | 본문 |
|---|---|---|
| 결과물 | 전체 · 문서 · 파일 · 이미지, 최근 파일 | 이름 · 만든 일 · 맡은 사람 · 최근 활동 표. 목록 · 격자 전환. 행을 누르면 만든 대화와 미리보기가 반반으로 열림. 대화 안 바로 답은 결과물에 없음 |
| 예약 | 새 작업, 활성(이름 + 다음 실행 · 주기), 일시 정지됨 › | 다음 실행, 주기, 맡은 사람, 결과 받는 곳, 요청, 지난 실행. 켜기 토글과 '지금 실행'. 예약이 없으면 아이콘 · 제목 · 예시 카드 |
| 앱 페이지 | 앱이 정함(예: GitHub 열림 · 병합됨 ›) | 앱 자기 화면(예: PR 목록과 그 PR을 맡은 구성원의 일) |
| 설정 | 일반 · 기억 · 구성원 · 기기 · 연결 · 앱 · 개선 · 권한 | 둥근 카드 안 '제목 + 컨트롤' 행. 저장 버튼 없이 바로 적용. [취소] [만들기]는 새로 만들 때만 |

설정 항목:

| 항목 | 내용 |
|---|---|
| 일반 | 이름, 브리핑 같은 기본값 |
| 기억 | 내가 말한 것(버전, 사용 중 · 결정 대기), 배운 것(근거, 주의, 나온 일), 변경 기록과 행마다 [되돌리기] |
| 구성원 | 하나와 구성원 목록(모델 그룹 이름, 작업 중 · 마지막 활성), 보관된 구성원 [보관 해제]. 행을 누르면 구성원 페이지 |
| 기기 | 이 Mac, 연결된 기기, 오프라인 기기와 다시 연결, 기기 연결 코드 |
| 연결 | 모델 그룹(맨 위 '기본'은 하나의 만들기 · 확인, 그다음 조사 · 코딩 같은 그룹), 구독 로그인, API 키. 확인 모델을 바꾸면 결정 카드 |
| 앱 | 설치됨, 추천. 앱마다 권한(도구 · 네트워크 · 파일 · 비밀 슬롯 · 이벤트), 추가하는 것(구성원 템플릿 · 스킬 · 절차 · 도구 · 화면), 버전과 '이 버전으로 되돌리기', 끄기. [설치]는 하나 대화에 결정 카드를 띄움 |
| 개선 | 결정 대기, 반영된 것과 되돌리기, 확인할 방법이 없어 버린 것 |
| 권한 | 두 칸 규칙: 항상 묻기 / 묻지 않고 허용. 규칙 추가 · 삭제. 지우면 다시 물음 |

| 기억 칸 | 내용 | 권위 |
|---|---|---|
| 내가 말한 것 | 명시 기억. 버전, 중지, 만료, 충돌 | 가장 높음 |
| 배운 것 | 학습 기억과 교훈. 근거, 적용 중인 버전, 확인된 효과, 되돌리기. 다음 일부터 적용 | 명시보다 낮음 |
| 구성원 기억 | 구성원별 홈 폴더의 기억. 1:1 대화의 '기억 후보'를 [남기기]로 남긴 것 포함 | 구성원 범위 |

**모델 그룹** ([ADR 0003](../architecture/decisions/0003-members-internal-teams-model-groups-and-apps.md) §3): 그룹 이름, 설명 한 줄(예: '출처를 찾아 읽고 근거와 함께 요약해요'), 모델 목록과 제공사, 사용하는 구성원. 편집 화면은 바로 적용입니다. 구성원은 설명을 보고 그룹을 고르고, 그룹 안 실제 모델은 호스트가 가용성 · 예산 · 계열로 고릅니다.

### 5.9 구성원

[ADR 0003](../architecture/decisions/0003-members-internal-teams-model-groups-and-apps.md) §1·§2·§8을 따릅니다.

- 처음에는 하나만 있습니다. 구성원은 소유자가 들일 때만 생깁니다. 직함은 없습니다.
- **들이기:** 같은 종류의 일이 되풀이되면 하나가 대화 안 결정 카드로 묻습니다('데이터 분석 일이 이번 달 4번 있었어요. 맡을 구성원을 추가할까요?' [구성원 추가] [나중에]). [구성원 추가]를 누르면 이름과 모양만 정합니다('새 구성원 만들기' [취소] [만들기]). 만들면 사이드바에 나타납니다.
- **1:1 대화:** 구성원마다 하나입니다. '하나가 넘김' 줄 아래 맡은 일 카드가 있고, 한 구성원이 두 일을 동시에 맡을 수 있습니다. 두 업무 방은 서로 다른 맥락입니다.

| 사용자가 한 일 | 어디서 | 어떻게 기록되나 |
|---|---|---|
| 그냥 말함 | 하나 대화 | 바로 답, 또는 일 카드(§5.4 기준) |
| 구성원에게 말함 | 그 구성원 대화 | 같은 기준 |
| 진행 중인 일에 대한 말 | 그 구성원 대화 | 그 일의 방향 바꾸기. '방향 바꿈: 일 이름' 줄. 감사 기록 |
| 일반적인 말 | 그 구성원 대화 | '기억 후보: …' 줄 [남기기] [지우기] |
| @이름으로 부름 | 하나 대화 | 그 구성원이 같은 줄기에 이름과 함께 답함 |
| 일시정지 · 중단 · 넘기기 | 정책 gate | 정책 gate가 권한을 검사하고 바로 처리. 새 구성원에게 넘기거나 권한을 넓힐 때만 결정 카드(§8). 감사 기록 |

- **구성원 페이지:** 프로필 팝오버의 '더 보기' 또는 설정 > 구성원. 스킬, 절차(건너뛸 수 있는 조건 포함), 모델 그룹, 앱, 최근 개선([자세히] [되돌리기], 자세히에는 출처 일 · 결과 · 확인한 쪽), 안 쓴 스킬 보관 줄, 예약, [보관].
- **스스로 만드는 스킬 · 절차 · 도구:** 문서 스킬과 절차는 확인을 거친 뒤 자동으로 반영되고 최근 개선에 남습니다. 진행 중인 일에서 소유자가 고쳐 말하면 그 일의 방향 바꿈으로 기록되고, 같은 고침이 절차 후보로도 열립니다. 업무 방에는 '절차 고침: … · 확인 대기' 줄이 보이고 확인 뒤에 적용됩니다(ADR 0003 §5). 권한을 넓히는 도구는 '직접 만든 앱'이 되어 그 구성원 대화에 앱 설치 결정 카드(하는 일 · 권한 · 확인 · 출처)로 묻습니다.
- 팀장과 팀원 같은 내부 계층은 화면에 없습니다. 일꾼은 일 카드와 업무 방의 역할 칩으로만 보입니다.

### 5.10 화면 문구 규칙

- **'비서'라고 부르지 않습니다.** 이름(예: 하나, 퀼)이 1인칭으로 말합니다. "맡았어요." 기억은 '기억'이라고 부릅니다.
- **직함을 쓰지 않습니다.** '부서장', '팀장', '부서', '조직'은 화면에 없습니다.
- **설명 문장을 두지 않습니다.** 부제, 동작 해설, 원칙 해설, 각주를 쓰지 않습니다. 라벨과 실제 내용만 남깁니다.
- **판정 기준:** "ChatGPT · Claude · Grok 화면에 그런 묶음 · 라벨 · 문장이 있나?" 없으면 지웁니다.
- 상태와 이름은 앱 관례 말을 씁니다: 완료, 실행 중, 확인 대기, 응답 대기, 작업 중, 마지막 활성, 나중에, 결과물, 앱. '결과 모름'은 Massion 고유 상태라 그대로 씁니다.
- 한국어 화면에 영어 진행형 문구를 섞지 않습니다.
- '다른 모델이 확인함' 같은 배지를 쓰지 않습니다. 읽지 않음 파란 점은 상태 표시라 씁니다.
- **첫 실행:** 로그인을 자동으로 찾습니다. 찾으면 바로 대화가 열리고 하나가 인사한 뒤 질문 하나와 선택지 A~D를 보입니다(입력창 '답변을 입력하거나 다른 이야기를 하세요'). 찾지 못했을 때만 계속하기 버튼(Claude로 계속하기 / ChatGPT로 계속하기)과 '다른 방법으로 계속하기'를 보입니다. 연결을 고르는 단계는 없습니다.

## 6. 누가 확인하나

사람이 AI가 한 일을 매번 확인하면 사람이 병목이 됩니다. Massion은 "사람이 승인한다"가 아니라 "만든 쪽이 스스로 판정하지 않는다"를 지킵니다.

- **자기 판정 금지.** 만든 쪽과 확인하는 쪽은 다릅니다.
- **확인하는 쪽:** 호스트가 소유한 결정론적 평가기, 또는 만든 모델과 **다른 계열(개발사)** 의 모델을 우선합니다. 둘 다 없으면 같은 모델로 따로 확인합니다(ADR 0003 §7). 모델은 "좋아 보인다"가 아니라 실행 증거로 판단합니다. 증거가 없으면 통과가 아니라 "확인 못 함"입니다.
- **사람은 미리 승인하지 않습니다.** 사람은 §8의 순간에만 결정합니다.
- **자율 단계 설정은 만들지 않습니다.** 묻지 않을 일은 설정 > 권한의 두 칸 규칙에서 정합니다(§17 2번).
- **신뢰는 기록으로 조절합니다.** 자동 반영했다가 나중에 되돌린 비율을 셉니다. 오르면 그 대상만 다시 꼼꼼히 봅니다.

다른 계열이 없으면 같은 모델로라도 따로 확인하고, 그 사실을 기록합니다. 같은 계열 확인은 일 결과를 받을 수 있지만 Growth와 스스로 만든 스킬 · 도구의 자동 채택에는 쓰지 못합니다([ADR 0003](../architecture/decisions/0003-members-internal-teams-model-groups-and-apps.md) §7). 이 사정을 소유자에게 알리는 방식은 아직 정하지 않았습니다.

현재: 실행자와 검증자는 다른 identity여야 하고 자기 검증은 domain에서 거부됩니다(구현됨). 계열(개발사) 구분은 아직 강제하지 않습니다. Growth 설계에 호스트 소유 계열 표가 제안되어 있습니다. 2026-11-04 실측은 Haiku 실행자와 Codex 검증자로 돌았습니다.

## 7. 정직성이 화면에 드러나는 방식 (예외만 말함)

독립 검증은 품질 공정이지 사용자가 읽을 문구가 아닙니다. '다른 모델이 확인함' 같은 배지는 쓰지 않습니다. 통과한 결과는 배지 없이 일 카드의 '자세히'로 근거를 엽니다.

| 안에서 일어난 일 | 사용자가 보는 것 | 시각 |
|---|---|---|
| 진행 중 | 일 카드 상태 한 줄, 사이드바의 빈 원 | 빈 원(`fg`) |
| 확인 통과 | 그냥 답이 옴. 배지 없음. '자세히' | 중립 글자(초록 없음) |
| 반려 후 고쳐서 통과 | 그냥 답이 옴. 일 상세에 "한 번 고쳤습니다" | 중립 |
| 고쳐도 기준을 못 맞춤 | "요청하신 조건 가운데 '정확히 한 줄'을 맞추지 못했습니다" + 조건 바꾸기 · 그만두기 · 확인 안 된 채로 두기 | `halt` 점 |
| 확인 못 함(검증 연결 실패 등) | 답에 한 줄: "확인하지 못한 결과입니다." | `halt` 점 |
| 결과 모름 | "보냈지만 응답을 받지 못했습니다. 중복될 수 있어 다시 보내지 않았습니다." + 예외 카드(종결 버튼) | `halt` 점 |
| 정할 일 | 결정 카드 | 노랑 |
| 종결(격리) | "종결됨 · 사유" | 중립 |
| 재시작 후 복원 | 보이지 않게 그대로 이어짐 | — |

'확인 안 된 채로 두기'는 수용이 아닙니다. 수용 Record를 만들지 않고, 결과물에 "확인하지 못한 결과"로 표시합니다. 결과 모름은 자동으로 다시 보내지 않습니다. 반려 뒤 새 시도는 같은 요청을 다시 보내는 것이 아니므로 이 원칙과 충돌하지 않습니다. 다만 자동 새 시도의 횟수와 한도는 아직 정하지 않았습니다(§17).

## 8. 사람이 결정하는 순간

사람은 두 종류만 그 순간에 결정합니다.

**A. 되돌릴 수 없는 외부 행동**

1. 돈 쓰기: 결제, 구매, 유료 신청.
2. 내 이름으로 보내기: 메일, 메시지, 게시, 양식 제출. 사람 경계를 넘는 이동도 여기에 듭니다. 다른 사람이 볼 수 있는 공간으로 옮기면 묻습니다. 나만 보는 공간 안에서 옮기면 알리기만 합니다.
3. 지우기.
4. 새 구성원 들이기: 에이전트 추가, 사람 팀원 합류, 외부 에이전트에게 처음 맡기기, 확장 설치.

**B. 확인 규칙·권한 변경**

5. 확인 규칙: 평가기, 검증 규칙, 모델 계열 표.
6. 권한 넓히기: 도구 범위, 네트워크, 예산, 승인 범위. 권한이 늘어나는 확장 업데이트도 다시 묻습니다. 권한 안에서 좁히거나 정리하는 변경은 묻지 않습니다.

**예외 처리(미리 승인이 아니라 생긴 일에 답함. 결정 카드가 아니라 예외 카드)**

- 결과 모름 종결(격리), 만료된 실행 종결.
- 고치지 못한 결과: 조건 바꾸기 · 그만두기 · 확인 안 된 채로 두기(수용 아님).

**묻지 않고 알리기만 하는 것:** 개인 기억을 나만 보는 결과물에 옮겨 적을 때(사람 팀원이 볼 수 있는 곳이면 위 2번처럼 묻습니다), 자동 반영을 되돌렸을 때, Growth 한도에 닿았을 때.

그 밖의 일(조사, 정리, 초안, 계산, 내부 작업, 기억·지시문 개선)은 그냥 합니다.

## 9. 능동 협업

비서와 구성원이 먼저 움직입니다. Grok Bot과 Paperclip이 쓰는 장치를 Massion 불변식에 맞춥니다.

| 장치 | Massion에서 |
|---|---|
| 먼저 하기 | 비서가 기억 · 일정 · 지난 일을 보고 먼저 제안하거나 시작 |
| 스스로 맡기 | 대표가 배정하되 구성원이 "제가 맡겠습니다"로 가져갈 수 있음 |
| 한 명만 잡기 | 배정은 원자적으로 한 명. 진 쪽은 재시도하지 않음(한 번만 보내기와 같은 원칙) |
| 깨어나기 | 주기 실행과 이벤트 트리거(새 메일, 일정, 실패한 일) |
| 감시 | 기록 · 정책 책임이 멈춘 일과 반복 실패를 비서에게 보고 |
| 메시지 상한 | 구성원끼리 주고받는 메시지 수에 안에서 상한. 사용자에게는 보이지 않음 |

현재: 스케줄러, 주기 실행, 모델이 묻고 답하는 루프가 없습니다. 안에서 도는 것은 실행자·검증자 2역할뿐입니다. 대표 · 기록 · 정책 gate와 스케줄러가 먼저 필요합니다.

## 10. 조직과 OS

조직과 OS는 화면에서 숨기지만 제품 범위에서는 되살립니다. 겉을 대화로 바꾸면 사용자는 "알아서 해 주는 조직"을 기대하는데, 지금 안에서 도는 것은 2역할뿐이기 때문입니다.

- **Core Office:** 여덟 이름(Atlas · Lyra · Quill · Onyx · Vega · Iris · Cedar · Sage)은 쓰지 않습니다. 여덟 책임은 호스트 기능(확인, 기록, 정책 gate, Growth, 예약, 편성, 기본 모델 그룹, 기본 스킬 · 절차)으로 되살립니다. 지금의 실행자와 검증자는 일의 만들기 자리와 확인 자리입니다([ADR 0003](../architecture/decisions/0003-members-internal-teams-model-groups-and-apps.md) §1).
- **조직:** 대표 하나와 소유자가 들인 구성원입니다. 안에서는 구성원이 일마다 팀장과 팀원을 띄웁니다(ADR 0003 §2).
- **되살리는 순서:** 대표(접수·응답) → 기록 → 정책 gate → 개선 → 앱.
- **아카이브 코드:** 기준선으로 쓰지 않습니다. 요구사항 단위로 골라 다시 들입니다(ADR 0001).
- **사용자가 OS를 고치는 길:** 말로 요청하면 결정 카드로 확정합니다. 구성원은 설정 > 구성원, 앱은 설정 > 앱에서 봅니다.

## 11. 인앱 도구 우선순위

기본은 대화 속 카드입니다. 크게 보려면 대화 옆 **작업 창**에 탭으로 엽니다(§5.5).

| 순서 | 도구·뷰 | 이유 |
|---|---|---|
| 먼저 | 결과물 미리보기(문서 · HTML · PDF · 표 · 이미지) | 맡긴 사람이 가장 먼저 보는 것. 읽기 전용이라 위험이 낮음 |
| 먼저 | 대화 속 진행 카드 | 이미 있는 Work 기록을 대화로 끌어온 것. 새 상태가 필요 없음 |
| 다음 | 인앱 브라우저 | API가 없는 웹 일에 필요 |
| 다음 | 결정 카드(스크린샷 · 금액 · 만료) | 브라우저와 짝 |
| 코딩 일 | 파일 · 변경 · 터미널 | 코딩을 맡길 때만 |
| 나중 | 에이전트 컴퓨터 화면 | 클라우드 컴퓨터가 없음. 다시 보기는 단계별 스크린샷으로 |

브라우저 규칙:

- 읽기(이동 · 보기 · 스크롤)는 그냥 합니다.
- 제출 · 결제 · 전송과 그것을 일으키는 클릭은 **한 번만 보내는 실행**입니다. 어느 쪽인지 모르면 실행으로 봅니다.
- 제출 뒤 응답이 끊기면 결과 모름입니다. 다시 제출하지 않고 주문 내역이나 보낸 편지함을 다시 읽어 확인합니다. 그래도 모르면 묻습니다.
- 도구가 성공이라고 해도 별도 확인 읽기와 스크린샷으로 검증합니다.
- 비밀값은 비서가 볼 수 없는 입력 폼으로 받습니다.
- 외부 에이전트(Claude Code · Codex CLI)의 자체 브라우저는 계속 끕니다. 지금도 Codex는 `shell_tool`, `unified_exec`, `browser_use`, `in_app_browser`, `computer_use` 등 도구 기능을 끄고, Claude Code는 도구 없이 실행합니다(`src/cli-agent-providers.ts`). Massion 자체 브라우저만 엽니다.

확장은 도구와 뷰를 함께 기여합니다. 자리는 세 곳입니다: 대화 카드, 작업 창 탭, 일 상세 안 탭. 뷰는 격리된 화면에서 그리고 Massion을 거쳐서만 실행합니다.

## 12. 공간

| 공간 | 내용 |
|---|---|
| 구성원 개인 공간 | 홈 폴더(성격 · 명시 기억 · 학습 기억 · 스킬)는 늘 남음. 작업 폴더와 브라우저 프로필은 구성원마다 일 단위로 따로 둠. 팀장과 일꾼은 일과 함께 끝나고 기억을 쓰지 않으며, 배운 것은 Growth 후보로만 남음 |
| 공통 공간 | 일마다 업무 방과 결과물 |
| 사람 팀원 | 합류는 '새 구성원'이라 한 번 물음. 사람마다 비서 대화는 비공개. 팀원 누구나 조사·작성을 시킬 수 있지만 "내 이름으로 보내기"는 주인만 |
| 연결된 PC | 기본은 이 Mac. 비서가 데이터와 저장소를 보고 고름. 실행 위치 칩은 이 Mac이 아니거나 오프라인일 때만 보임. 칩을 바꾸면 새 일에만 적용. 호스트가 잠들면 실패가 아니라 일시정지 |
| Reason 기기 | Reason으로 연결된 기기는 소유자 본인 것이라도 외부 구성원으로 다룸. 결과는 확인 전까지 모름 |
| 기억 | 설정 > 기억(§5.8) |

사람 경계를 넘는 이동만 묻습니다. 다른 사람이 볼 수 있는 공간으로 옮기면 묻습니다. 나만 보는 공간 안에서 옮기면 알리기만 합니다. 실행 권한(폴더 · 호스트 · 브라우저)과 자기수정 권한(기억 · 지시 채택)은 두 축으로 따로 둡니다. 구성원의 정체성과 기억은 실행 공간이 바뀌어도 남습니다(scope.md 불변식).

## 13. 외부 에이전트

다른 서비스의 에이전트는 Massion 조직의 정식 구성원이 아니라 계약직처럼 다룹니다. 특정 네트워크에 묶지 않고 **외부 구성원 어댑터** 하나로 감쌉니다. 프로바이더를 연결 방식별 factory로 나눈 지금 구조와 같은 방식입니다.

- 첫 어댑터: Reason Network(로컬 코딩 에이전트와 호스팅 비서를 잇는 네트워크).
- 두 번째 어댑터: 표준 A2A.

조건:

1. **도착은 처리가 아닙니다.** 답이 올 때까지 결과 모름입니다.
2. **같은 요청을 두 번 보내지 않습니다.** 실행 하나마다 멱등 키를 고정합니다. 붙이기 전에 실제로 한 번만 도착하는지 시험합니다.
3. **외부 결과도 검증합니다.** 같은 독립 확인을 거칩니다. 화면은 여전히 예외만 말합니다.
4. **받은 글은 데이터입니다.** 지시로 읽지 않습니다.
5. **신뢰 범위를 좁게 시작합니다.** 처음에는 사용자 본인 머신의 에이전트만. 본인 머신이라도 Reason으로 연결되면 외부 구성원이고, 결과는 확인 전까지 모름입니다. 팀원이나 호스팅 봇에게 처음 맡길 때 한 번 묻고, 그다음은 기억합니다.

현재: INT-01은 연결된 제품 경로가 없습니다(requirements.md).

## 14. 코딩 Work, Growth, 구현 순서

### 14.1 코딩 Work (pstack에서 가져옴)

- 큰 코딩 일은 혼자 착지·검증할 수 있는 하위 Work로 나눕니다. 하위 Work마다 기준과 검증 하나.
- 스택은 Work 의존입니다. 부모 Work의 수락된 산출물(커밋)이 자식 Work의 고정 입력입니다.
- 아래부터, 검증된 구간만 자동으로 착지합니다. 첫 미검증 지점에서 멈춥니다.
- 병합·push는 다시 읽어 확정합니다. 되읽기에 실패하면 결과 모름이고 다시 보내지 않습니다.
- 루프 한 바퀴 = 변경 하나 · 검증 하나 · 기록 한 줄. 버린 시도도 Record에 남깁니다.
- 반복되는 교정은 에이전트가 가장 강한 층(구조 → 정적 검사 → 지침 → 문서)에 고정합니다. 지침 · 문서 층과 규칙을 좁히는 변경은 다른 계열 모델의 확인을 거쳐 자동 반영하고, 버전을 남기고, 되돌릴 수 있습니다. 정적 검사 · 검증 규칙 · 평가기를 바꾸는 고정은 확인 규칙 변경이라 결정 카드(§8 B)로 묻습니다.

현재 기반: 소유자가 정한 순서로 Work를 차례로 돌리는 경로(run sequence)와, 앞 Work의 수락된 Record를 요구하는 선행 조건(prerequisites)이 있습니다. 코드 변경·병합·push 경로는 없습니다.

### 14.2 Growth

설계는 [growth-reflection-and-model-proposals.md](../architecture/growth-reflection-and-model-proposals.md)를 따릅니다. 일곱 단계 가운데 1~2단계를 설계했습니다.

1. 실행 기록(reflection trail): 끝난 Work 하나를 결정론적으로 읽기 전용 투영. 행동은 그대로.
2. 모델이 제안하는 기억 후보: 측정된 개선이 있으면 소유자를 기다리지 않고 자동 채택. 되돌린 비율로 보정(calibration). 명시 기억을 대체하는 후보는 자동 채택하지 않고 결정 카드로 묻습니다. 기본이 자동이라는 것은 ADR 0002의 결정이고, 설계 문서도 이에 맞춰 자동/검토 선택을 없앴습니다.
3~7. 평가기 추가, 효과 관찰, 프롬프트·도구 안내 대상, 교훈 라이브러리, 정책·조직 대상.

화면: 설정은 없습니다. 정상적으로 자동 채택된 것은 대화에 올리지 않고 설정 > 기억의 '배운 것'에만 남깁니다. 대화에는 예외만 올립니다: 되돌림, 한도 도달, 명시 기억을 대체하는 후보. 묻는 것은 확인 규칙 · 권한을 바꿀 때뿐이고, 결정 카드로 묻습니다.

현재: 설계 문서 상태는 "proposed design, not implemented"입니다. 구현된 것은 소유자 제안, 호스트 반올림 oracle 평가, 소유자 채택·되돌리기입니다.

### 14.3 구현 순서

도그푸딩 걸림돌과 같은 순서입니다.

1. **기본 실행 경로와 영속 연결.** 재시작 뒤에도 권한과 기본 실행자·검증자가 남아야 매일 쓸 수 있습니다.
2. **비서 대화.** 대표가 대화하고, 일이면 Work를 만듭니다.
3. **Growth 1단계 실행 기록.**
4. **계열 지도와 모델 그룹.** 계열 검사(같은 계열 확인은 허용하되 기록)와 설명으로 고르는 모델 그룹.
5. **v3 골격 1.** 레일, 사이드바(하나와 구성원 자리), 활동 목록, 작업 창.
6. **v3 골격 2와 정책 gate.** 대화 안 일 카드, 접힌 작업 줄, 결정 카드를 내는 정책 gate, 예외 카드.
7. **구성원.** 6번의 정책 gate가 있어야 합니다. 이름 붙인 구성원, 1:1 대화, 업무 방.

그다음은 배정과 스스로 맡기, 조직 Growth, 앱, 스스로 만드는 스킬 · 도구, 외부 구성원입니다(ADR 0003).

## 17. 남은 질문

1. 반려 뒤 조직이 스스로 고쳐 다시 내는 횟수와 한도는 얼마인가? 이 정책은 불변식 문서에 들어가야 합니다.
2. 영속 권한의 모양은 무엇인가? 프로토타입은 결정 카드의 '다음부터 그냥 해'를 지우고 설정 > 권한의 두 칸 규칙(항상 묻기 / 묻지 않고 허용)으로 옮겼습니다. ADR 0002 §6(카드에서 배우는 권한)을 이에 맞게 고칠지, 그 규칙과 지금의 Mission 범위 권한(scoped grant)을 같은 것으로 볼지 정해야 합니다.
3. 명시 기억을 대체하는 후보를 결정 카드로 묻는 것을 '소유자 지시를 바꾸는 일'로 보는 해석이 맞는가? 지금 문서는 그렇게 정했습니다. 소유자가 직접 쓴 스킬을 바꾸는 후보도 같은 규칙입니다.
4. 모델 계열 표는 누가 처음 채우는가? 표에 없는 모델은 같은 계열로 봅니다. 다른 계열이 없으면 같은 모델로 확인하고 기록합니다(ADR 0003 §7). 이 사정을 소유자에게 어떻게 알리는가?
5. 바로 답할지 일로 넘길지의 기준은 정했습니다(§5.4). 그 판단은 누가 확인하는가? 일로 잘못 넘기면 비용이 생기고, 바로 답으로 놓치면 책임이 사라집니다.
6. 기준 초안은 대표가 씁니다. 사용자는 업무 방에서만 봅니다. 기준이 틀렸을 때 고치는 길은 대화로 충분한가?
7. 구성원 간 메시지 상한은 얼마인가? Reason Network는 에이전트 쌍마다 10분에 12건을 씁니다.
8. 같은 비서를 Slack · 텔레그램 · 메시지 앱에서 부르는 것은 이번 범위에서 뺍니다. 자리를 비웠을 때 결정 카드를 받을 곳은 그동안 무엇인가?
9. 아침 브리핑의 '의미 있게 새로운 것'은 어떻게 정하는가?
10. **작업 창 분할 규칙.** 새 탭은 지금 창에 붙는가, 새 창으로 나뉘는가? 창은 최대 몇 개인가? 결정 카드의 근거 페이지가 열려 있을 때 다른 일의 업무 방을 열면 어떻게 되는가?
11. **예약의 범위.** 예약은 소유자만 만드는가, 하나나 구성원이 제안해서 만들 수도 있는가? 결과는 늘 맡은 사람의 대화로만 가는가? 예약 실행이 돈 쓰기나 보내기에 닿으면 그때마다 결정 카드인가? 구성원 예약이 깨울 때 예산은 누구 것인가?
12. **고정.** 사이드바의 '고정'은 지웠습니다. 행 우클릭 '고정'을 그릴 때 '고정됨'으로 다시 넣는가?
13. **비서 이름.** 첫 실행에서 이름 정하기 단계를 뺐습니다. 첫 실행 뒤 이름을 정하라고 언제 권하는가? 바꾸는 곳은 설정 > 일반입니다.
14. **예산과 백업의 자리.** 설정 목록(일반 · 기억 · 구성원 · 기기 · 연결 · 앱 · 개선 · 권한)에 예산과 백업 자리가 없습니다. 일반 아래인가, 따로 두는가?
15. **소유자 기억과 구성원 기억의 경계.** 일마다 필요한 부분만 읽기 전용으로 붙이고 사본은 두지 않는 안이 있습니다. 1:1 대화의 '기억 후보'는 구성원 기억에만 남는가, 하나의 기억에도 남는가?
16. **구성원 들이기 제안 기준.** '이번 달 4번' 같은 숫자는 가설입니다. 제안이 거절되면 얼마 동안 다시 묻지 않는가? 오래 쓰지 않은 구성원을 보관하는 기간은 얼마인가?
17. **결정을 한 번에 모으기.** 정할 것이 여러 개 쌓이면 결정 카드 한 장에 번호를 붙여 모으고 질문마다 추천 답을 붙일 것인가? 일은 결정을 기다리며 멈추지 않고, 답을 받으면 새 실행으로 이어 가는 방식(Matt Pocock `software-factory`, `grilling`)과 맞출 것인가?
18. **확인 안 된 채로 두기.** 프로토타입은 모든 예외 카드를 [다시 시도] [닫기]로 줄였습니다. ADR 0002 §8의 '확인 안 된 결과를 그대로 두기'(수용 아님)와 §7 표의 선택지는 어디서 고르는가?
