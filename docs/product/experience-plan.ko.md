# Massion 사용자 경험 기획 (프로토타입 기준 문서)

- 상태: 초안 v1, 2026-11-04
- 시각 기준: Massion 디자인 시스템(https://claude.ai/artifact/7BWR6jSZ9FtZJcfFGfsFc8), 근거는 massion-archive `apps/desktop/DESIGN.md`
- 프로토타입: Massion 프로토타입 Design 캔버스(https://claude.ai/artifact/XYTuX4ZXwqyKvpcRVuDBRF). §7의 A1~A9 아홉 화면과 공유 레일, 화면마다 구현 상태 메모가 있습니다. 두 링크 모두 소유자 비공개입니다.
- 기능 기준: `docs/product/scope.md`, `docs/product/requirements.md`, 실측 증거 `docs/acceptance/live-vertical-slice-ui-evidence.md`
- 이 문서는 화면을 그리기 위한 기획입니다. 화면마다 **구현됨 / 일부 / 계획**을 표시해, 프로토타입이 곧 구현 목록이 되게 합니다.

## 1. 왜 다시 기획하는가

2026-11-04에 첫 수직 흐름을 실제 모델과 브라우저 UI로 완주하면서 기능은 동작한다는 것을 확인했습니다. 동시에 지금 화면으로는 매일 쓸 수 없다는 것도 확인했습니다.

| 실측한 마찰 | 원인 |
|---|---|
| Work 한 건을 돌리는 데 Mission 작성, 권한 2개, Work 작성, 접힌 섹션 펼치기, 실행자·검증자·권한·상한 선택, 확인, 실행까지 10단계 이상 | 기능마다 양식이 하나씩 추가되었고, 사용자 업무를 기준으로 화면을 묶은 단계가 없음 |
| 한 페이지에 접힌 양식이 30여 개 | 정보 구조 없음. 모든 기능이 같은 높이에 나열됨 |
| 실행 버튼이 접힌 `<details>` 안에 있음 | 가장 자주 쓰는 동작이 가장 깊이 숨어 있음 |
| 권한 목록에 ID만 보임(수정됨) | 사람이 읽을 이름을 보여 주는 규칙이 없었음 |
| 재시작하면 권한이 사라지고, 매번 모델을 직접 고름 | 연결·권한이 세션 메모리에만 있음 |
| 기준(criteria)을 사용자가 직접 문장으로 작성 | Mission 해석 지원이 없음 |
| 마케팅 문구 히어로, 베이지 카드, 영어 개발자 문구 | 시각 기준 부재(AI 기본값으로 회귀) |

## 2. 사용자와 핵심 장면

- **사용자:** 자기 기기에서 Massion을 운영하는 한 명의 소유자. 개발자이지만, 매번 내부 구조를 다루고 싶어 하지는 않습니다.
- **핵심 장면:** 사람이 목표를 맡기고, 조직이 묻고·반론하고·넘겨주며 일하는 것을 읽다가, **사람이 필요한 순간에만** 개입합니다. AI가 실행하는 모습이 아니라 조직이 책임지는 모습을 보여 줍니다.

## 3. 핵심 업무 (Jobs)

| # | 업무 | 시작 → 끝 | 목표 단계 수 | 현재 |
|---|---|---|---|---|
| J1 | **맡기기** | 한 문장으로 목표를 입력 → 조직이 Mission·Work·기준 초안을 제안 → 확인하면 실행 시작 | 3 (입력 → 초안 검토 → 시작) | 일부: Mission/Work 생성과 대화→Work 전환은 있음. 기준 초안을 모델이 제안하는 기능은 없음 |
| J2 | **진행 보기** | 업무 목록에서 Work 선택 → 협업 방에서 실행·검증 흐름을 읽음 | 1 | 일부: 실행자·검증자 Effect와 판정은 있음. 메시지 흐름으로 보여 주지 않음 |
| J3 | **결정하기** | 수신함의 결정 → 해당 Work의 결정 블록 → 승인/거절 | 2 | 일부: 결정 종류(기억 채택, 결과 모름 처리, 만료 종결)는 있음. 수신함이 결정을 모아 주지 않음 |
| J4 | **반려 이해·수정** | 반려된 Work에서 이유 확인 → 수정 Work 시작 | 2 | 구현됨(양식 형태): 반려 이유, 수정 Work 연결 |
| J5 | **결과·근거 확인** | 수용된 Work → 산출물, 검증 체크, Record, checksum | 1 | 구현됨(양식 형태) |
| J6 | **기억·개선** | 기억 저장 → 개선 제안 → 평가 → 채택 → 효과 관찰 → 되돌리기 | 결정 1회당 2 | 일부: 반올림 oracle 하나만 평가 가능. 모델이 제안하는 개선은 없음 |
| J7 | **연결·예산** | 프로바이더/구독 연결 → 기본 실행자·검증자 → 한도 | 처음 1회 설정 후 0 | 일부: manifest 기반 연결은 있음. 영속 연결, 기본 경로, 달러 한도는 없음 |

**원칙:** 매일 쓰는 경로(J1→J2→J3)는 **첫 설정 이후 3단계 안에** 끝나야 합니다. 모델과 권한은 기본값(J7)에서 오고, 사용자는 바꿀 때만 고릅니다.

```
운영                     행: 제목 / 상태·시각        결정 블록은 흐름 안에서 제자리        작업 단계 n / N
  홈 · 업무 · 지식                                 하단: 입력창(지시·방향 바꾸기)
  조직 · 개선

설정
```

|---|---|---|
| 수신함 | 사람이 필요한 결정만 모아 해당 화면으로 보냄. 결정을 소유하지 않음 | 계획 |
| 홈 | 오늘의 진행·차단·결정 요약, 빈 상태에서 J1 입구 | 계획 |
| **업무** | 4영역 Work 화면. 제품의 중심 | 일부(기능은 있고 화면이 없음) |
| 지식 | 문서 원본·관계·영향 범위 | 일부(정확한 버전 관계와 문서 캡처는 있음) |
| 조직 | 책임과 역할, 조직 개정 | 일부(실행자·검증자 2역할만) |
| 개선 | 기억, 개선 제안, 평가, 채택·되돌리기, 효과 | 일부(반올림 oracle만) |
| 프로바이더 | API·구독 CLI 연결, 모델, 상태 | 일부(manifest 연결은 있음, 영속 연결 없음) |
| 예산 | 실행별 사용량, 한도 | 일부(출력 토큰 예약만, 달러 한도 없음) |
| 설정 | 호스트, 저장소, 백업 | 일부 |

## 5. Work의 상태 (모든 화면이 정직하게 보여야 함)

| 상태 | 사용자에게 보이는 말 | 시각 | 다음 행동 |
|---|---|---|---|
| 초안 | 초안 · 시작 전 | 점선 행(`row--draft`) | 검토 후 시작 |
| 실행 중 | 실행 중 · 실행자 | `fg` 점, 메시지 흐름 진행 | 지켜보기 · 방향 바꾸기 · 취소 |
| 검증 대기 | 검증 중 · 검증자 | `fg` 점 | 지켜보기 |
| **반려** | 반려됨 · 검증자 이유 | `halt` 점, 반론 메시지 | 이유 보기 → 수정 Work |
| **결과 모름** | 결과를 알 수 없음 · 다시 보내지 않음 | `halt` 점 + 결정 블록 | 격리(영구 종결) 결정 |
| 수용 | 완료 · Record | 중립 글자(초록 없음) | 산출물·근거 보기 |
| 격리 | 종결됨 · 사유 | 중립 | 기록 보기 |
| 재시작 후 복원 | (보이지 않게 그대로 이어짐) | — | — |

`fixture`와 `real-provider`, 구독 CLI처럼 검증 강도가 다른 실행은 참여자 줄에 증거 수준으로 표시합니다.

## 6. 핵심 흐름

1. **맡기기(J1):** 홈 또는 업무 헤더의 `새 업무` → 입력창에 한 문장 → 조직(대표)이 초안 카드를 제안(목적, 기준, 실행자/검증자, 예산) → `시작`. 기준 초안은 사람이 고칠 수 있고, 고친 내용이 원본으로 기록됩니다. *(현재: 사람이 기준을 직접 씀 → 계획)*
2. **반려 → 수정(J4):** 협업 방에 검증자 반론 메시지(반박한 내용을 인용) → 그 아래 `수정해서 다시 시작` → 원래 Work와 연결된 새 Work. *(현재: 수정 양식이 별도 섹션 → 화면만 계획)*
3. **결과 모름(J3):** 실행자 메시지 자리에 상태 줄 "결과를 알 수 없습니다. 다시 보내지 않았습니다." → 결정 블록(무엇: 영구 격리, 왜: 응답 유실, 되돌리기: 불가) → `승인`/`거절`. *(현재: 격리 양식 있음 → 화면만 계획)*
4. **기억 개선(J6):** 개선 서피스에서 제안 → 평가 결과(기준 1/3 → 후보 3/3) → 수신함에 결정 → 결정 블록에서 `승인` → 다음 Work의 참여자 줄 옆에 "적용 기억 rounding@2" → 되돌리기도 결정 블록. *(현재: 기능 구현됨, 화면 계획)*

## 8. 기획의 빈 곳 (프로토타입이 답해야 할 질문)

1. Mission과 Work를 사용자에게 따로 보여 줄 것인가, 아니면 Work만 보이고 Mission은 "목적"으로 숨길 것인가?
2. 기준 초안을 누가 쓰는가? 대표가 제안하고 사람이 확정한다면, 그 제안은 어떤 모델이 하고 어떻게 검증하는가?
3. 실행자·검증자 기본 경로는 어디서 정하는가(프로바이더 서피스 vs Work마다)? 기본값을 바꾸면 과거 Work는 그대로인가?
4. 지금은 실행자와 검증자 두 역할뿐입니다. 아카이브의 다중 에이전트 협업 방을 어디까지 실제 기능으로 만들 것인가? 프로토타입에서는 두 역할로 그리고, 다중 에이전트는 `계획`으로 표시합니다.
5. 수신함이 모아야 할 결정의 전체 목록은 무엇인가?
6. 구독 CLI와 API 키 경로의 증거 수준 차이를 일반 사용자에게 어떻게 한 줄로 설명할 것인가?
