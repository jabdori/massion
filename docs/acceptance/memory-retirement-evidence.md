## Behavior and preserved evidence

Owner-only `retire-memory` names exact memory identity/version plus nonempty reason. Only a currently effective explicit version in the Mission scope can be retired. It changes only `effective` to false. Immutable content/source/scope/authority/id/version and old Work/attempt/accepted Record pins remain unchanged; exact original task data still resolves. Subsequent Work excludes that instruction while retaining other effective memory. A strictly advancing explicit version can reactivate deliberately through existing save-memory.

`ProductService.retireMemory` dispatches the existing application CAS/fingerprint path with primitive copied fields and trusted local-owner actor. Normal `POST /missions/:id/memory-retirement` accepts only commandId/expectedRevision/memoryId/version/reason. It rejects forged scope/authority/actor/extra fields; domain rejects missing, inactive, superseded, learned and wrong-scope target, invalid version/reason and non-owner registered roles. This does not introduce production authentication or persistent per-Mission user identity.

The existing atomic journal retains the exact retirement reason/event with no outbox effect. Command keys were added to portable journal reconstruction, so retained snapshot/event transitions remain validated rather than treated as unknown. No storage schema or snapshot migration is needed; no physical deletion or history rewrite occurs. Exact duplicates replay the original committed snapshot; changed-payload identity conflicts and losing concurrent edits cannot fall back to a newer memory version.
